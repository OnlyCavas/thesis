** Trusted Execution Environment Integration
:PROPERTIES:
:CUSTOM_ID: impl_tee_integration
:END:

*** Enclave Structure
:PROPERTIES:
:CUSTOM_ID: impl_tee_enclave_str
:END:

Until this point, the proof-of-concept has already presented mitigations for ensuring *Confidentiality* and *integrity* by leveraging QUIC's mechanics and implementing software mitigations, alongside integrations with *I2P* via a SAM bridge, providing a way for the user to remain anonymous within a swarm. Currently, there is no verifiable, trusted way to guarantee that a swarm participant is using a trustworthy client implementation and that the participant actually computed the proof-of-work necessary for swarm admission, and other sensitive operations.

As depicted in Section {{{ref(impl_tee_integration)}}}, the TEE layer is responsible for providing a mechanism to determine whether a peer is, in fact, authentic and running a trustworthy client implementation before admission into the swarm. The integration is structured in two distinct components. The first is the enclave, written in C, running within a Keystone {{{citep(tee_keystone)}}} trusted execution environment in complete hardware isolation from the host operating system. The second is a host-side C++ runner that interfaces with the Keystone SDK to load and manage the enclave's life cycle. Similarly, the client communicates with the runner via a C FFI layer, allowing Rust to invoke enclave operations without directly depending on the Keystone SDK while maintaining type safety across the boundary.

Keystone needs to deploy aggregated components so the enclave can run in a foreign environment {{{citep(tee_keystone)}}}. To simplify deployment, the enclave binary, along with the Eyrie runtime and loader, is directly embedded into the {{{mark(bqti)}}} final binary at compile time and later extracted to a temporary directory on demand. This approach produces a self-contained binary with all necessary components, facilitating its distribution without needing a separate enclave installation on the target machine. On top of that, it actually solves a major problem with enclave updates and client version matching, by binding a {{{mark(bqti)}}} version to a specific enclave hash, allowing swarm maintainers in a future implementation to choose what versions are allowed.

Given the memory constraints of an enclave environment, not every cryptographic library is suitable. With this in mind, libraries that pre-allocate large buffers or depend on OS primitives are incompatible with the enclave's limited execution model. As a result, {{{mark(TweetNaCl)}}} was integrated for Ed25519 signing as it computes incrementally without pre-hashing, and {{{mark(libtomcrypt)}}} for hashing (SHA2-256), since Keystone's built-in cryptographic support only covers SHA3. Both libraries are statically linked with the binary along with the Keystone SDK. Notably, since Keystone's Security Monitor uses Ed25519 with SHA3-512 as the internal hashing function rather than the standard SHA2-512, the standard Ed25519 verification libraries already integrated are incompatible with the attestation report generated by the Keystone enclave. This compatibility was achieved by using the audited {{{mark(ed25519-dalek)}}} curve implementation, along with SHA3-512 in place of the standard SHA2-512, thereby enabling both software and TEE-supported devices to attest to TEE peers.

*** Keypair and Sealing Key
:PROPERTIES:
:CUSTOM_ID: impl_tee_kp_sealing_key
:END:

Upon initialisation, the enclave derives its Ed25519 key pair deterministically from Keystone's {{{mark(sealing key)}}}, which is a hardware-rooted secret bound to both the enclave measurement and the physical device. Consequently, the same binary, running on the same hardware, will always produce the same Ed25519 key pair. In contrast, any modification to the binary or execution in a different environment will yield a different key. This is the fundamental property that sustains the security model, maintaining its identity across restarts and being unforgeable without the exact hardware and binary combination. Crucially, its private key can never leave the enclave, to ensure this, each cryptographic operation explicitly wipes it from enclave memory before returning anything to the host. Thus, taking the necessary security measures to ensure that a compromised host process cannot recover it, and effectively break the trust anchor.

*** Enclave Capabilities
:PROPERTIES:
:CUSTOM_ID: impl_tee_enclave_capabilities
:END:

The current enclave implementation exposes exactly five functions to host from a shared protocol header:

Each request follows the same structure and life cycle: it begins by initialising the enclave, sending the request, and awaiting the corresponding typed response via {{{mark(Keystone OCALL)}}}. Once read, destroys the enclave before returning to the host. It is worth noting that the private key is wiped after the end of each life cycle, regardless of the operation performed.

*** Proof of Work
:PROPERTIES:
:CUSTOM_ID: impl_tee_proof_of_work
:END:

To ensure that the joining peer actually wasted computational power calculating the proof-of-work, when the TEE is enabled, that operation is moved within the enclave. It iterates SHA256 over the concatenation of its {{{mark(public\_key)}}}, the received {{{mark(challenge)}}} value, and an incremental {{{mark(nonce)}}} until the resulting hash satisfies the correct number of leading zeros for a given difficulty target. Once the winning hash is found, the result is immediately signed with the enclave's Ed25519 private key and returned to the host. This approach is fundamentally stronger than a software-only proof-of-work, because the signature over the hash proves that the computation was actually performed within a trusted environment using a hardware-rooted private key. Notably, an attacker cannot forge a valid response without the private key, which never leaves the enclave. By relying on TEE for the proof-of-work calculation, it simultaneously proves both computational effort and hardware authenticity.

Signing with the enclave's private key would break compatibility with the software certificate system, where each protocol extension generates its own leaf certificate key pair. This issue is solved by keeping the enclave's public key constant across generated certificates. As a result, each leaf certificate carries different metadata, but is signed by the same underlying hardware-rooted key, ensuring that the DHT identifier matches the same key that signed the proof-of-work, thereby allowing any peer to verify it later using the peer's DHT identifier, regardless of whether the peer supports TEE.

*** Remote Attestation
:PROPERTIES:
:CUSTOM_ID: impl_tee_remote_attestation
:END:

{{{figure(diagrams/067/keystone-attestation.pdf, Keystone attestation report chain of trust)}}}

Apart from computational effort, leveraging TEE remote attestation capabilities allows guaranteeing that a remote peer is trustworthy without needing a PKI in place. The attestation report generated by Keystone comprises a three-layer chain of trust rooted in the device's hardware. The first layer is the *Security Monitor* report, which contains the measurement hash and public key, both signed by the device's hardcoded hardware key using Ed25519 with SHA3-512. The second layer is the *Enclave Report*, containing the {{{mark(enclave\_hash)}}} that reflects the enclave's immutability: if the enclave's code is modified, it produces a different hash. The report keeps the attested nonce, which, in the {{{mark(bqti)}}} case, is the computed proof-of-work signed by the *Security Monitor*. The final layer is the enclave's {{{mark(device public key)}}} itself, embedded as the trust anchor at the root of the chain.

In light of the above, the verification process follows a reverse-layer approach. Starting by matching the {{{mark(dev\_pub\_key)}}} with the enclave's trusted key, which is distinct for each device once in production. After that, the *Security Monitor Signature* must be valid under the same {{{mark(dev\_pub\_key)}}}, and the *Enclave Signature* must be valid with the *SM Key*. Once verified, the enclave hash can optionally be compared against a hardcoded expected value to confirm whether the enclave code has been modified and guarantee that the factory code is running within the TEE, which is the optimal mechanism for detecting binary tampering. At last, the embedded nonce in the report data is verified against the challenger-supplied real nonce, preventing an attacker from replaying an intercepted valid report.

An enclave trust anchor relies on the {{{mark(device public key)}}}. However, in the current implementation, this is intentionally relaxed, being hardcoded or even ignored. For instance, in a production environment deployment, the device key would need to be signed by a centralised third-party authority, similar to how Intel SGX and TDX rely on Intel's attestation service, contradicting the initial statement of achieving a proof-of-concept ({{{mark(bqti)}}}) entirely decentralised. To avoid this dependency, instead the trust anchor lies in {{{mark(a public manifest file)}}}, currently with the following structure:

#+begin_src json
[
  {
    "version": "0.1.0",
    "enclave_hash": "4855bd98e..."
  }
]
#+end_src

As a result, each {{{mark(bqti)}}} version ships with a matching {{{mark(enclave\_hash)}}} exposed in a signed manifest, using the developer's private key, which never leaves the device, effectively binding it to an enclave measurement. Hence, peers verify the enclave hash from the report attestation against the manifest rather than the hardware certificate chain, thereby preserving full decentralisation and allowing any user to verify and attest to the enclave measurement manually.

It is worth acknowledging that this approach does not remove third-party trust entirely. It shifts it from a hardware manufacturer to a project maintainer. Unlike Intel's attestation service, the manifest is publicly auditable, and the enclave hash is independently reproducible by anyone building it from source, making the trust assumption transparent and verifiable. Additionally, enabling a swarm maintainer in a future version to establish swarm admission requirements, with enough information to decide which {{{mark(bqti)}}} versions are allowed or whether TEE is mandatory.

Nonetheless, this approach carries its own attached risks. Recent supply chain attacks have targeted developers' signing keys as a viable attack vector {{{citep(ohm2020)}}}. Taking Node.js packaging as an example, where highly interdependent dependency trees allow a single compromised package to propagate malware across thousands of downstream consumers as legitimate software {{{citep(chain_attacks)}}}. Similarly, a compromised developer signing key would allow pushing a malicious enclave hash measurement as a trusted version, silently breaking the trust anchor. Despite remaining as an open problem and known limitation of a developer-signed trust model in general, similar models like Linux package signing address this partially through PGP key revocation, but ultimately, the strongest mitigation is transparency. Meaning, open-source code means the enclave hash is independently reproducible by anyone, making silent substitution detectable and extremely hard to break.

*** Backend Abstraction and Feature Flag
:PROPERTIES:
:CUSTOM_ID: impl_tee_abs
:END:

To keep the client as modular as possible and avoid binding it to a specific TEE implementation, TEE support is optional at compile time via the {{{mark(--features tee)}}} compilation flag. Without it, a client falls back to software-only authentication transparently, with no code changes required. This approach compiles only the necessary operations into the binary. Furthermore, depending on the target processor architecture, a different TEE backend can be compiled. The current implementation provides the RISC-V {{{mark(Keystone)}}} backend. It already implements the baseline to support more backends, abstracting away the underlying TEE implementation. For example, an ARM {{{mark(OP-TEE)}}} backend could be integrated in the future.

To support multiple backends under the same API, all enclave operations are accessed through the {{{mark(TeeExecute)}}} trait, defining the four attestation methods: {{{mark(proof-of-work)}}}, {{{mark(signing)}}}, {{{mark(public key retrieval)}}}, and {{{mark(attestation)}}}. Additionally, the same abstraction pattern is extended for the certificate integration, defined by {{{mark(ActiveKeyIdentity)}}}, which changes with its corresponding compilation feature, switching its underlying behaviour. Finally, the report attestation is carried by a default enum that specifies the attestation type: {{{mark(KeystoneReport)}}}. Upon bootstrap admission, a verifying peer verifies a report attestation differently depending on the report type, with its concrete implementation baked into the {{{mark(bqti-tee)}}} library, which acts as a middle ground between the {{{mark(FFI)}}} and {{{mark(bqti)}}}.

*** Identity Integration
:PROPERTIES:
:CUSTOM_ID: impl_tee_identity
:END:

Similarly, TEE is integrated through the same {{{mark(KeyIdentity)}}} abstraction layer used by the software certificate path. When compiled with TEE support, {{{mark(TeeKeyIdentity)}}} replaces the software implementation, silently delegating QUIC TLS signing to the enclave, without changing any aspects at the transport layer. As already established in Section {{{ref(impl_kademlia_routing_identity)}}}, node identity is derived from the original certificate, which in the TEE case is generated from the enclave public key, and then repeated across all protocol layers. With TEE enabled, that key is hardware-bound, elevating the same single key design from a software-only assumption to a hardware guarantee.
