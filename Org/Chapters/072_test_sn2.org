** Scenario 2: Adversarial Mitigation and Attack Detection
:PROPERTIES:
:CUSTOM_ID: eval_sn2
:END:

This scenario evaluates the effectiveness of the implemented security mitigations against three specific attack vectors. Each attack is executed by a dedicated malicious peer compiled with the corresponding adversarial feature flag, leveraging the Rust compiling system. The main objective is to demonstrate that the security layers are modular and operate independently at their protocol boundaries, without modifying the honest client code. Hence, demonstrating where attacks are detected and handled by the DHT and BEP layers, preventing adversarial nodes from interacting with the other extensions.

| Attack vectors  | Feature flags | Defense layers | Mitigation actions |
|--------+----------+------------------|
| Token Forgery Attack  | {{{mark(ml\_forge\_token)}}} | DHT admission  | Connection closed |
| Replay Attack  | {{{mark(ml\_replay\_token)}}} | DHT admission  | Connection closed |
| Piece Substitution Attack  | {{{mark(ml\_piece\_sub)}}} | BEP piece verification  | Piece dropped |

*** Token Forgery Attack
:PROPERTIES:
:CUSTOM_ID: eval_sn2_token_forgery
:END:

During the previous test case, the malicious remote peer, already compiled with the following feature flag {{{mark(ml\_forge\_token)}}}, was waiting for the manifest file to establish a connection with the target swarm. Notably, without first completing the admission proof honestly to gain entry to the swarm, the adversarial peer doesn't know the bootstrap public key. On software-only devices, the bootstrap public key is transient and changes on every restart. At the same time, TEE-capable bootstraps retain the same key since the sealing key is hardware-bound.

Once admitted to the swarm network, it queries the network using information gathered from the torrent's manifest. It begins by challenging the seeder with a self-signed, fabricated token. During the initial handshake, the seeder queries the received token for {{{mark(swarm\_id)}}}, which is the SHA-256 hash of the swarm's publicly known PGP certificate, which the seeder must load before swarm admission. In either case, the connection is terminated, preventing further interaction with the malicious peer, if none of the loaded certificate hashes matches the token's {{{mark(swarm\_id)}}} or if the signature verification fails using the correct swarm's PGP public key.

For the remainder of the test case, the malicious peer enters a loop trying to reconnect and challenge the bootstrap again, but fails to authenticate with the seeder each time and is rejected from the routing table.

*** Replay Token Attack
:PROPERTIES:
:CUSTOM_ID: eval_sn2_replay_token
:END:

Analogously, the previous adversarial instance is terminated and recompiled with the {{{mark(ml\_replay\_token)}}} flag. As a result, it simulates a peer intercepting another peer's token and replaying it back to an available seeder. Instead of capturing a valid token, the malicious peer, during the initial P2P handshake, concatenates a random challenge, completely ignoring the one provided by the challenger. Then it sends the bootstrap-valid token, along with the random challenge and the signature of their concatenation, back to the seeder (challenger).

{{{figure(testbed/stwo/012-seeder-interceptiong-replay.pdf, Seeder detecting replay attack, ownership proof failed, attack="token\_replay" logged, connection terminated)}}}

Upon receiving the handshake submission, the seeder recomputes the expected signature by concatenating the token hash with the challenge it had established. Since the malicious peer randomly picked a nonce instead of the real challenge, the signature verification fails. Furthermore, even in a real-world scenario where an adversary intercepts a valid handshake submission, the replay could still fail. Since the nonce is single-use and the signature is bound to the DHT identity derived from the original peer's private key, the attacker cannot produce a valid signature for the correct challenge without that key.

{{{figure(testbed/stwo/013-replay_failed.pdf, Malicious peer submitting forged nonce, skipping handshake, thus being removed from routing table after consecutive rejections)}}}

Currently, both bootstrap admission and P2P authentication challenges have a 30-second window. They are bound to the DHT identity and its IPv4 address, short enough to attest peers and protect against these types of attacks. Therefore successfully rejects further interaction among swarm participants and forces any attacker to solve a fresh proof-of-work to gain legitimate admission.

*** Piece Substitution Attack
:PROPERTIES:
:CUSTOM_ID: eval_sn2_piece_subs_attack
:END:

This section assumes that the adversarial remote peer is already legitimately bootstrapped and authenticated with a leecher peer, that is requesting a pipeline of sequential pieces to be transferred. The previous adversarial instance is terminated and recompiled with {{{mark(ml\_piece\_sub)}}}, modifying the default seeding behaviour. Instead of correctly seeding the piece data along with its matching piece index, ({{{mark(sha256( index | piece data ))}}}) tries to deceive the leecher by randomising the piece index, thereby simulating a piece-substitution attack to destabilise the piece pipeline and corrupt the data, making the leecher struggle to obtain all the pieces.

Additionally, the leeching node is compiled with TEE capabilities and runs within a Keystone RISC-V virtual machine. Therefore, proving that both software-only and TEE-capable nodes can coexist within the same swarm, with different attestation levels that are shown as the test cases evolve.

{{{figure(testbed/stwo/014-bootstrap-attestation.pdf, TEE leecher remote attestation verified, manifest resolved to expect measurement *0x4855bd98*, hardware attestation *report accepted*)}}}
@@latex:\label{fig:attestation}@@

{{{figure(testbed/stwo/015-sig-failed.pdf, TEE leecher detecting piece substitution attack, consecutive piece signature verification failures)}}}

Both peers begin by being admitted within the swarm, proving their identities to the bootstrap node. Unlike the malicious node, the leecher is assigned a higher trust level, as shown in Figure @@latex:\ref{fig:attestation}@@. Upon admission, the leecher queries the DHT for available seeding nodes and then starts the download pipeline. For each received piece of data, the leecher verifies its hash concatenation {{{mark(sha256( index | piece data ))}}} with the locally cached piece index. If the match fails, the leecher automatically rejects the piece, discarding it and requesting a replacement until it finds an honest seeder and completes the download.

Across all three attack vectors, the security mitigations operated as designed. Admission attacks were intercepted at the DHT layer, preventing an adversarial peer from further interacting with the rest of the protocol extensions implemented. Piece-level corruption was caught at the BEP layer, dropping malicious pieces without stalling the download or requiring manual intervention. The layered design ensures that compromising one layer does not cascade to the others, preserving the modularity claim established in [[#poc_design_goals][Section 3.2]].
