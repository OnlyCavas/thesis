In this section, the two most popular anonymity overlays, *Tor* and *I2P*, are compared to understand their differences.

Tor and I2P share the same goal of anonymous communication but differ fundamentally in their design philosophies. Tor was built for anonymous ClearNet access, offering low-latency web browsing by relying on a bidirectional volunteer-operated circuit to anonymise user activity. I2P was built as a self-contained darknet, optimised for internal P2P communication, and operated by volunteer nodes. These anonymity solutions directly influence BitTorrent's performance, scalability, and that model.

# A practical key difference between *Tor* and *I2P* lies in their interface implementations, which affect the effort required to build or adapt applications to run on these overlays, such as BitTorrent.

# cite Privoxy

In the case of *Tor*, it uses the standard {{{gls(socks)}}} proxy interface, which allows any application that supports it to route traffic through *Tor*, such as a web browser. More precisely, the Tor client will act as a local proxy, routing the configured traffic through the network. Even though it is possible to pipe traffic through Tor, the SOCKS interface only transmits TCP packets, which limits the performance of some P2P protocols that benefit from UDP, as well as some DHT operations and extensions. Additionally, some messages may leak metadata, including User-Agent strings and HTTP headers, unless filtered by an additional layer, for example, *Privoxy* [cite].

On the other hand, *I2P* provides a native middleware API rather than a general-purpose proxy. Applications must either be explicitly adapted to implement I2P's streaming or be designed and built with I2P integration in mind, which results in higher development costs and better control over the anonymity properties. I2PSnark is an example of a BitTorrent client built natively for I2P.

The SOCKS interface is compatible with virtually any proxy-aware application; for example, using an open-source proxychains to pipe normal application data through SOCKS, thereby pushing its traffic through the Tor network, but it could leak data. In contrast, some applications integrate directly with I2P, such as Susimail and 2IpMail for emailing and I2PSnark for torrenting. However, some I2P clients implement a SAM bridge interface, a protocol-agnostic API that serves as a linking layer between protocols such as QUIC and I2P.

Another critical factor is scalability when considering anonymity overlays, given high churn and bandwidth-intensive applications. Both overlays face different challenges, and the architectures that solve them perform differently.

Tor's circuit-based design relies heavily on volunteer-operated relays. As the number of clients increases, network traffic will grow significantly, leading to congestion and bottlenecks. Tor is not truly decentralised, relying on centralised {{{gls(hsdirs)}}} to both distribute and store routing metadata. Consequently, overloading or compromising HSDirs could disrupt the service directory or even inject malicious descriptors.

On the other hand, *I2P* is fully decentralised, relying on a distributed database NetDB, a Kademlia variant with Floodfill peers. The DHT is distributed among Floodfill peers, meaning no single peer can control the network's topology or consensus. Furthermore, its decentralised nature provides multiple targets, thereby increasing resilience against single points of failure and allowing the network to scale naturally with user growth.

In high-bandwidth, high-churn scenarios, Tor's reliance on centralised directories could exacerbate congestion as the swarm grows. In contrast, the I2P distribution model scales with user demand, distributing load across nodes by creating specialised inbound and outbound tunnels, inherently performing better for large-scale, high-churn P2P file sharing. I2P tunnels have a default lifespan of 10 minutes before being rebuilt for privacy, introducing a modest overhead.
