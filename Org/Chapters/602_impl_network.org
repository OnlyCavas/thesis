** Peer Connectivity and Stream Multiplexing
:PROPERTIES:
:CUSTOM_ID: impl_quic_config
:END:

As depicted in Section {{{ref(poc_bt_over_quic)}}}, a single QUIC connection is maintained for the entire BitTorrent session with each remote peer. All protocol traffic is multiplexed over this connection using independent QUIC streams of different types, such as:

+ *Control streams*

  Unidirectional streams are dedicated to control traffic {{{mark(DHT)}}}, {{{mark(PEX)}}} and {{{mark(BEP)}}} messages. Each peer maintains its own outbound control stream, meaning a stall or backlog on one peer's control stream does not block the other peer's.

+ *Bidirectional Streams*

  These are used for single major requests and are thus associated with data transfer. A new bidirectional stream is opened for each piece request, and it is responsible for delivering the piece blocks that compose the final piece, enabling higher fidelity and performance while allowing fine-grained multiplexing and independent flow control per request. As a result, if a piece request stalls, it does not block all the others.

{{{figure(diagrams/062/quic-connection.pdf, QUIC's connection topology\, multiplexing of both a single unidirectional (control signals) stream\, and several bidirectional streams (piece exchange))}}}

All incoming stream handlers across all active peer connections run concurrently as independent tasks, each feeding into a single central dispatch channel that is consumed sequentially by the main loop, as illustrated in [[#fig:recv-stream][Figure 4.3]]. Meanwhile, a slow or stalled stream will never block its sibling from delivering to the channel, buffering incoming packets with a capacity of {{{mark(1024)}}} queued messages before any producer would feel the backpressure. This approach keeps the actor model in one place, allowing the main loop to route each arriving packet to the correct handler based on its protocol {{{mark(ID byte)}}}, without requiring locks or synchronisation across concurrent readers. By default, the implementation caps concurrent connections at 50 swarm participants, keeping the buffer well within its capacity under normal load.

*** Packet Topology
:PROPERTIES:
:CUSTOM_ID: impl_quic_packet_topology
:END:

# [change: !!! Actually correct implementation, make that compatibility man]
Each packet, regardless of protocol, is assembled identically on the wire:

#+begin_example
[ 4 bytes: big-endian length ][ 1 byte: protocol ID ][ payload ]
#+end_example

The first one-byte ID discriminates the protocol carried in the payload, following the BEP specification:

| protocol ID  | Constant | Protocol         |
|--------+----------+------------------|
| {{{mark(0x00)}}} | (zero length) | Keep-alive    |
| {{{mark(0x09)}}} | 9  | DHT (BEP 5)                |
| {{{mark(0x14)}}} | 20       | BEP 10 extension (PEX, metadata)      |
| {{{mark(0x13)}}}   | 19       | BEP handshake (standard)     |

A keep-alive is a special case: a four-byte zero frame that carries no ID byte or payload and serves only to maintain the connection alive. The payload is serialised using Bencode, which is the natural encoding for DHT, as established by BEP 5, and was extended uniformly to PEX and BEP messages for consistency. The change was motivated by keeping a simpler codec that handles three protocols after the ID byte is read. However, a trade-off is justified by the absence of any QUIC-native BitTorrent implementation to date. Additionally, bidirectional streams extend the default packet by adding a reply handle, allowing the requesting stream to respond without additional routing.

*** Connection Management
:PROPERTIES:
:CUSTOM_ID: impl_quic_management
:END:

The current implementation of the {{{mark(Connection Manager)}}} handles three edge cases that arise within the {{{gls(poc)}}} network context: *self connections*, *simultaneous dials*, and *duplicate dial attempts*.

To prevent self-connection attempts before the handshake even begins, the implementation rejects them as early as possible. When the endpoint is bound to the unspecified address {{{mark((0.0.0.0))}}}, the manager determines the endpoint's actual outbound IP by probing a local UDP socket. Later, it compares this resolved address and port against the target peer's address. A match on both is rejected immediately.

Fixing simultaneous dials where two different peers attempt to connect at the same time is solved by comparing the socket addresses lexicographically. If the local address is lower than the peer's, the incoming connection wins and the outgoing connection is terminated, thereby replacing it. As both sides evaluate the same underlying comparison, they always converge on the same connection without coordination.

Finally, duplicate dial attempts are prevented by checking in-progress handshakes. Before opening a new connection, the manager checks both established connections and in-progress dials under a read lock, thereby preventing races without holding a write lock across the network round-trip. Holding a write lock across a network round-trip would block all incoming connection attempts until it is freed, impacting performance and stalling traffic.

The endpoint is abstracted behind a NetworkEndpoint enum that handles connection and acceptance details regardless of whether the underlying transport is standard QUIC or I2P, allowing {{{mark(bqti)}}} to swap the routing implementation transparently.
