** Transport Layer: BitTorrent over QUIC
:PROPERTIES:
:CUSTOM_ID: poc_bt_over_quic
:END:

As established in Chapter 2 (see [[#quic_intro][Section X.X]]), QUIC solves many limitations of TCP and UDP in P2P environments. This section details how QUIC is integrated as the sole transport protocol within the proposed architecture, replacing both TCP and UDP and eliminating the need for uTP.

A unique QUIC connection is established per peer when the first torrent session initiates a connection, in contrast to a traditional BitTorrent client, which may open multiple TCP connections to the same peer for different purposes. Establishing a single connection per peer reduces connection overhead, significantly simplifying connection management, as all streams are controlled by a single connection that shares a congestion window and flow control context.

The connection lifespan is scoped to the client rather than to a single torrent session. Once a peer is discovered, whether through DHT lookups, PEX gossip, or a tracker announcement, a QUIC connection is established and remains open until either peer shuts down or the client session is actively terminated. Consequently, if two peers already have established a healthy QUIC connection when a new torrent is added, that same connection is used. Therefore, all torrent sessions share the same underlying connection, avoiding redundant connection establishment and prioritising control stream reuse over the overhead of a new connection. This approach is suited for long-running clients that participate in several swarms simultaneously, reducing the cost of negotiating new connections across shared activity.

Furthermore, leveraging QUIC's native multiplexing, two types of streams operate concurrently over each connection. Specifically, for protocol control signalling, each peer maintains a dedicated outbound unidirectional stream towards its connected counterpart. Together, these two unidirectional streams form a logical bidirectional connection control channel over which DHT RPC messages, PEX gossip, and BEP control messages, such as handshake and bitfield, are exchanged between the two parts. This design aims to keep each peer in full control of its own outbound signalling, avoiding congestion on a shared stream. In contrast, for piece transfer, each concurrent piece request is assigned an independent bidirectional stream, allowing the requester to send the piece request and receive the corresponding blocks within the same stream context. A sliding window of approximately 5 to 10 concurrent piece streams is maintained to respect the BitTorrent-recommended piece throughput. Crucially, a stalled or slow piece stream doesn't affect any other ongoing transfer, as each stream is fully independent from the others, a property TCP cannot achieve without relying on multiple connections.

For instance, consider a similar implementation over TCP. Achieving the same concurrency with a dedicated control channel and multiple independent piece streams would require opening a new TCP connection to the same peer for each stream. Thus, it incurs its own three-way handshake and TLS negotiation, resulting in at least one RTT per connection. Nonetheless, TCP's delivery model is fundamentally sequential within a single connection, meaning a lost or delayed packet stalls all subsequent data, regardless of which piece it belongs to, and precisely the Head-of-Line blocking problem discussed in Chapter 2 (see [[#utp_tracker][Section X.X]]).

On the other hand, uTP, while reducing bandwidth contention, inherits the same sequential constraint. QUIC eliminates both issues within a single connection, with independent streams unaffected by packet loss on sibling streams, and the handshake cost is amortised across all concurrent activity. Also, if the connection is dropped mid-session and then reestablished, QUIC manages this with 0-RTT.

All things considered, the transport layer is implemented using the quinn crate, which is a Rust-based async-native QUIC implementation built on top of tokio, the async runtime used throughout the proof-of-concept. This library was chosen for quinn's full RFC 9000 compliance, ease of usage, and natural integration with the tokio ecosystem, aligning with the project's security requirements and goals. Further details regarding quinn integration, connection management, stream life cycle and configuration are discussed in Chapter 4.
