*** Core Concepts and Design Principles of QUIC

Starting in 2012, Google addressed these limitations by developing a new Application Layer protocol, QUIC (Quick UDP Internet Connections) {{{citep(quic_google)}}}, aiming to reduce the latency of web traffic by eliminating TCP bottlenecks while maintaining the same level of security. That said, modifications to the TCP protocol often require an update to the Operating System, as QUIC is a user-space protocol that uses UDP as its transport layer, making new changes easier. On top of that, QUIC enables it to traverse middleboxes, because most Firewalls and NATs don't block UDP packets. Also, by encrypting and authenticating each packet, we can prevent middleboxes from tampering with it. To solve the dependency on TCP, QUIC relies on the *User Datagram Protocol* UDP for the transport layer protocol. Similar to HTTP/2, QUIC also supports multiplexed streams that run over a single UDP connection between two endpoints; a unique 64-bit ID identifies each stream. That said, whether a packet is lost within one of the streams doesn't affect the others, allowing the client and server to exchange data without stalls. Its main objectives are to provide privacy and security, reduce the attack surface at the transport layer (e.g., reflective attacks, amplification, and resource exhaustion {{{citep(quic_004_41)}}}), and improve latency per request, helping mobile devices connect faster across different networks. In 2021, QUIC was standardised by the IETF and has been growing ever since, with big techs like Facebook, Gmail, Instagram, Google Chrome, and YouTube {{{citep(quic_005_2)}}}.

TCP connections maintain a sequential packet delivery, guaranteeing that packets arrive in the order the server initially sent them. For instance, in case the packet 5 arrives earlier, the *Upper Layer Application* must stall the connection until the order is corrected, imposing a delay denoted as {{{gls(hol)}}} {{{citep(quic_005)}}}. QUIC solves this by supporting *multiplexing* data streams, thereby creating multiple data streams over *one QUIC connection* {{{citep(quic_006)}}}. Due to multiplexing, receiving out-of-order packets only stalls one stream, while maintaining a normal flow on the others. Streams on QUIC are lightweight abstractions that provide a bidirectional byte stream, useful for framing application messages handling a maximum of 264 bytes {{{citep(quic_007)}}} per stream. An ID identifies each stream, assigning an odd and an even ID to the client and the server, respectively, to avoid collisions.

To complete a single TCP connection, an initial full three-way handshake is required, adding at least 1-RTT of overhead before any data exchange. Combined with TLS 1.3 negotiation, resulting in at least 2-RTT, and with TLS 1.2, up to 3-RTT. QUIC addresses both issues by integrating TLS 1.3 natively into the handshake, making it mandatory rather than optional. By natively supporting TLS, it can enforce security by authenticating and encrypting the packet header and payload without an extra round-trip, achieving 1-RTT overhead per new connection. However, for resumed or previously established connections, QUIC supports 0-RTT resumption by embedding a 64-bit Connection ID in every packet, enabling the client and server to re-establish the connection without a new handshake. For instance, load balancers use connection IDs to forward traffic to its intended destination. Rather than relying on a 5-tuple (IP and port), as with TCP, QUIC uses a connection ID to identify connections even when the IP address changes, making it particularly useful for mobile devices that often change IPs as they switch networks. Once established, connections can migrate seamlessly to other networks {{{citep(bt_005)}}} without disrupting any active services. However, 0-RTT resumption introduces a slight security tradeoff, making resumed connections vulnerable to replay attacks.

More precisely, QUIC employs several procedures to establish and resume connections efficiently. As explained earlier, if a client has previously cached information about a known server, such as connection ID, keys, transport parameters, it can immediately establish an encrypted connection with the server and send application data in a 0-RTT packet without a new handshake. However, if the client doesn't support the server's QUIC version, they initiate a version negotiation exchange until both agree on a common version {{{citep(quic_004_16)}}}.

On the other hand, for a full initial handshake with no prior communication between the two, the procedure typically completes in 1-RTT. The client starts by sending an *initial packet* containing a TLS Client Hello along with QUIC's parameters. After receiving the message, the server replies with an *initial packet* containing a Server TLS Hello, encrypted extensions, and its certificates. Finally, the client completes the handshake with a TLS Finished message, often complemented by application data, completing the 1-RTT {{{cite(quic_005)}}}.

A QUIC packet structure consists of two main sections, namely the *Header* and *Payload*. The *header* contains the routing metadata, which is paramount for being forwarded to the right destination. During the first interaction between the endpoints, it tends to be larger because it includes additional negotiation metadata, such as QUIC's version and other connection parameters. The *payload* comprises the remaining bytes of the packet, containing the embedded application data.

Additionally, QUIC tries to decrease latency caused by packet loss by proactively sending redundant data for critical packets, sacrificing about 5% of bandwidth to reduce retransmission latency. The authors note that, according to Google, this feature reduces retransmissions by 8% despite modest bandwidth overhead {{{citep(quic_001_17)}}}. QUIC achieves this by having each packet carry a new packet number, while others carry retransmitted data. Therefore, it solves the TCP ambiguity problem by distinguishing the ACK for a message from its retransmission. Another mechanism is *flow control*, which limits the receiver's buffer size to avoid congestion that blocks the receiver from intercepting the rest of the packets from other streams.

QUIC uses UDP as its underlying transport-layer protocol, benefiting from lower latency by avoiding TCP's built-in congestion control and reducing ordering overhead. However, QUIC solves this issue by implementing its own congestion control mechanism at the application layer. Google reimplemented the TCP-Cubic {{{citep(quic_002_5)}}} congestion algorithm, while allowing developers the freedom to implement or choose their own congestion mechanisms.

Standard QUIC implementations often underperform optimised TCP+TLS stacks due to user-space overhead and kernel networking inefficiencies, such as interrupts, context switches, and system calls. The authors developed {{{mark(picoquic-dpdk)}}} {{{citep(quic_003)}}}, a modified version of the IETF picoquic stack. They chose {{{mark(picoquic)}}} because of its minimal implementation that follows IETF standards and its underlying C implementation, which meant it could be easily extended and simple to work with. Instead of using the Linux Kernel, it uses the {{{gls(dpdk)}}}, designed to improve packet processing workloads. It applies several performance optimisations by enabling {{{gls(pmd)}}}, zero-copy processing, NUMA-aware memory allocation, and huge pages, eliminating kernel intervention and bypassing the kernel networking stack.

In further evaluations, their implementation {{{mark(picoquic-dpdk)}}} achieved three times the throughput of the vanilla {{{mark(picoquic)}}} and produced results comparable to those of the optimised TCP+TLS stack in single-core mode. Additionally, it surpasses other QUIC stack implementations in performance, such as {{{mark(msquic)}}}, the Microsoft implementation, {{{mark(quicly)}}}, an implementation designed primarily for H2O, and {{{mark(quiche)}}}, the Cloudflare implementation. That said, bypassing the Linux Kernel improved the overall performance of QUIC, even though QUIC stacks focus on performance, such as {{{mark(msquic)}}} and {{{mark(quicly)}}}, their implementation outperforms them.
