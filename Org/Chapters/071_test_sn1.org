** Scenario 1: Functional Validation
:PROPERTIES:
:CUSTOM_ID: eval_sn1
:END:

This scenario establishes the experimental baseline by verifying the functional correctness of the custom {{{mark(bqti)}}} BitTorrent client under non-adversarial conditions. The main objective is to evaluate whether a software-only client *leech-soft* executing on *Machine 2* and a virtualised hardware-isolated client *leech-tee* executing sensitive code operations within a Keystone enclave on *Machine 1* can successfully discover peers, perform mutual authentication, and complete a full file set transfer without data corruption.

*** Swarm Bootstrapping and Peer discovery
:PROPERTIES:
:CUSTOM_ID: eval_sn1_booting
:END:

Before any transfer, each joining node must solve a *difficulty = 24* proof-of-work puzzle. At this difficulty level the puzzle requires an adversary to find a nonce whose resulting hash falls strictly below a target of $2^{256-24} = 2^{232}$, equivalently requiring the first 24 bits to be zero, thereby requiring a computation on average $2^{24}$ ($16{,}777{,}216$) SHA256 iterations to forge a single identity successfully. Considering only software operations on *Machine 1*, to establish a realistic baseline for admission cost, the {{{gls(pow)}}} calculation execution time was measured across $10{,}000$ iterations on *Machine 1*.

| Metric | Value |
|--------+-------------------------|
| Mean                | 801.06 ms  |
| Median (P50)        | 554.52 ms  |
| 95th percentile     | 2370.09 ms |
| Iterations          | 10,000     |

Considering a *difficulty = 24*, at the median admission cost of {{{mark(554.52 ms)}}} per identity, generating $1{,}000$ fake identities would require approximately {{{mark(9.2 minutes)}}} of sustained computation, rising to {{{mark(92.4 minutes)}}} for $10{,}000$ fake identities. Under the 95th percentile cost of {{{mark(2370 ms)}}}, the cost increases to {{{mark(39.5 minutes)}}} and {{{mark(6.6 hours)}}} respectively, showing that even in a favourable scenario for the attacker, large-scale Sybil attacks or derived attacks are economically impractical without specialised hardware.

| difficulty level  | bit shift | 1000 identities | 10 000 identities |
|-------------------+-----------+---------------+-------------------|
| 24 (Measured) | $2^{0}$ = 1   | ~9.2 minutes | 1 hour and 32.4 minutes |
| 28 (Inferred) | $2^{4}$ = 16  | ~2.5 hours | 24 hours and 38.7 minutes |
| 32 (Inferred) | $2^{8}$ = 256 | ~39.4 hours | 16 days and 10.4 hours |

Considering the results across the difficulty levels, *difficulty = 28* represents the optimal middle ground between usability and security in a software-only environment. A legitimate admission costs approximately {{{mark(8.87 seconds)}}} per DHT identity, which is acceptable for a one-time join operation and valid for a 30-minute lifespan (standard token validity). For an adversary attempting to generate $1{,}000$ fake identities at this difficulty, this would theoretically take approximately {{{mark(2.5 hours)}}} and {{{mark(24.65 hours)}}} of sustained computational effort to achieve $10{,}000$ fake identities.

It is also worth noting that the measured times reflect software execution on Machine 1 (x86). While TEE-based proof-of-work within a Keystone RISC-V emulated environment will be significantly slower due to the emulation overhead, making difficulty=24 already a higher cost for TEE peers. However, in the case of TEE peers, the admission computational cost becomes secondary because the attestation report already provides a hardware-rooted identity guarantee that no computational cost can replicate. Although not the primary admission barrier for TEE peers, it remains required as an additional security layer.

*** Secure File Transfer
:PROPERTIES:
:CUSTOM_ID: eval_sn1_secure_file_transfer
:END:

With swarm admission verified, this phase evaluates the end-to-end functional correctness of the data transfer pipeline across a heterogeneous swarm composed of both native software (*leech-soft*) and TEE (*leech-tee*) remote peers. To assert the download integrity, an {{{mark(arch\_linux.iso)}}} image, along with its official cryptographic manifest {{{mark(sha256sum.txt)}}}, serves as an evaluation payload.

This configures a testing environment to rigorously evaluate the client behaviour during an active file data transfer, verifying that the downloaded data matches the given {{{mark(.torrent)}}} manifest and that its reconstruction completes successfully without any data corruption.

As previously stated in [[#impl_kademlia_network_join][Section 4.4.3]], any peer can act as a bootstrap node, defining alone or with more nodes a swarm, being the swarm's trust anchor. It is configured manually, generating a PGP key pair and signing its {{{mark(bqti)}}} CA root certificate with it. Once it generates the PGP signature, it is automatically recognised as a bootstrapping node. Then, a swarm maintainer must load their PGP public key into the client and distribute it across all participating nodes before swarm initialisation.

{{{figure(testbed/scone/001-bootstrap-ini.pdf, Bootstrap node loading PGP signed CA root certificate)}}}

Once the bootstrap is active and running, the swarm maintainer is responsible for configuring the seeder by specifying the bootstrap node's IPv4 address as the swarm entry point. The client supports multiple bootstrap nodes, though only one is configured in the test case. The seeder generates the {{{mark(.torrent)}}} metadata file from the target payload.

Once built, the seeder detects the bootstrap node from that same manifest and initiates the admission process by computing the proof-of-work and submitting it for verification, as illustrated in [[#fig:seeder-bootstrap-complete][Figure 5.3]]. In parallel, the manifest {{{mark(.torrent)}}} is shared with the other nodes so they can add it to their download queues and begin the same admission process. Upon acceptance, the bootstrap issues a signed token to callers, which they use with the loaded PGP certificates to ensure that it is, in fact, a trustworthy bootstrap.

Meanwhile, the leecher will add the same {{{mark(.torrent)}}} manifest provided by the seeder, and the {{{gls(bt)}}} state machine will automatically detect a new possible bootstrap node from the manifest file and initiate the admission process. Once admitted, it queries the DHT for nearest seeders, using the torrent's info hash as the search key. For each one discovered, it sends interest and awaits unchoking. Once unchoked, it fills its pipeline with request pieces, with a maximum of 128 concurrent block pieces, as detailed in earlier sections.

Once the download is complete and the last piece is verified, the internal state machine creates a symlink in the user's current directory to its internal downloads directory named *download*, similar to the Nix approach {{{citep(nix_ref)}}}. Then, it transitions to the seeder, reloading the inner files and creating the respective hard links to them.

{{{figure(testbed/scone/007-leech-transition.pdf, Download completing at 2949/2949 pieces, symlink created and state transitioning to seeding)}}}

Finally, using the downloaded {{{mark(sha256sum.txt)}}} to verify the {{{mark(arch\_linux.iso)}}}, confirming that the download completed successfully without any data corruption.

The completed {{{mark(arch\_linux.iso)}}} payload (~{{{mark(1.5 GB)}}}, 2949 pieces) was transferred over a direct QUIC connection on the local network in approximately {{{mark(13.14 seconds)}}}, achieving a throughput of roughly {{{mark(112.22 MB/s)}}} ({{{mark(897.79 Mbps)}}}), close to the practical maximum of a gigabit link (~940 Mbps), establishing a baseline against which the I2P-routed overhead is evaluated comparatively in [[#eval_sn3][Section 5.4]]. On the other hand, over a {{{mark(WiFi)}}} link the same transfer dropped to {{{mark(29.1 MB/s)}}} ({{{mark(232 Mbps)}}}), while in loopback, with no network overhead the stack sustained {{{mark(220.68 MB/s)}}}, including per-piece signing and verification.
