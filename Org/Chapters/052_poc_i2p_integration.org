** Anonymity Layer: I2P Integration
:PROPERTIES:
:CUSTOM_ID: poc_i2p_integration
:END:

As discussed in Chapter 2 ([[#tor_vs_i2p][Section X.X]]), I2P is better suited for P2P networks than Tor due to its decentralised NetDB, unidirectional tunnels, and its design as an internal darknet rather than an anonymising proxy. On top of that, Tor maintainers actively discourage the use of BitTorrent over Tor, claiming it harms others on the network. Nonetheless, I2P's properties make it a perfect fit for the proof-of-concept use case, where peers communicate directly rather than accessing external resources.

Although I2P might seem a good choice for anonymity, a natural question arises:

#+begin_quote
/Is QUIC necessary when I2P already provides encrypted, routed communication between peers?/
#+end_quote

Despite I2P properties solving some of these issues, it does not address transport-level concerns such as stream multiplexing, flow control, or Head-of-line blocking. Therefore, in a way, both complement each other on these matters: QUIC handles reliable, multiplexed transport between peers, while I2P ensures that the underlying communication remains anonymous.

To achieve this integration with the I2P network, all QUIC traffic is handled by a local SAM bridge, which exposes a socket-based API that allows applications to interact with I2P traffic without implementing their own I2P router. SAMv3 supports some stream types (*STREAM*, *DATAGRAM*, *RAW*, *DATAGRAM2*, *DATAGRAM3*). *STREAM* provides reliable order delivery, and *DATAGRAM* provides unreliable unordered delivery analogous to UDP. Since QUIC is built on top of UDP and provides its own reliability and ordering guarantees, a DATAGRAM session is the appropriate choice for bundling QUIC's packets. For instance, using a STREAM session could introduce redundant mechanisms or even break QUIC's congestion control assumptions.

In detail, this integration is achieved by binding the quinn endpoint directly to the locally exposed UDP socket of the SAM DATAGRAM session. Upon session establishment, a UDP socket is bound to a preconfigured local port that serves as the bridge between quinn and the I2P SAM interface. Consequently, the SAM bridge intercepts outbound UDP packets and wraps them as I2P DATAGRAM messages. These are then forwarded to the local I2P client daemon, thereby connecting to the real I2P network. Inbound packets follow the reverse path: i2pd delivers them to the local SAM UDP socket, and quinn intercepts and processes them, extracting the QUIC payload required for both data and QUIC's control mechanisms. As a result, this design maintains an abstraction between the transport and anonymity layers, allowing seamless I2P integration to be disabled without requiring modifications to the transport layer or any other component of the proof-of-concept.

The I2P client daemon chosen for this integration is *i2pd*, a lightweight, non-Java I2P client written in C++ that implements the I2P protocol. It was chosen for its significantly lower resource footprint and startup overhead, making it suitable for programmatic deployment alongside the client. Moreover, there is an open-source Docker image enabling reproducible deployments across different environments. On top of that, for testing and simulation purposes, i2pd is deployed as a single host interface to the I2P network, where all peers establish a UDP connection to proxy their traffic over I2P. Thus, it is imperative to have a consistent tunnel configuration across development, simulation, and production environments.

Despite providing an anonymous layer on top of QUIC, I2P introduces a latency overhead that significantly impacts download performance. All things considered, this is an accepted tradeoff given the threat model established in [[#poc_threat_model][Section X.X]], and its actual impact is further evaluated in Chapter 5 (see [[#eval_sn3][Section X.X]]). Nevertheless, the client can disable I2P and use the default transport layer, leveraging QUIC's full capabilities to achieve higher download speeds.
