** Kademlia DHT
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_bep_extension
:END:

As introduced in [[#distributed_hash_tables][Section 2.1.9]], BitTorrent's mainline DHT is based on Kademlia. This section details how the concrete implementation diverges from the stock protocol, the additional security mitigations applied on top, and the core decisions made.

*** Routing and Node Identity
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_routing_identity
:END:

# (citeme: Kademlia, read the video to be sure)

According to the paper, stock Kademlia assigns each node a 160-bit identifier derived from SHA1. That identifier determines the node's position in the Key Space, organised into 160 k-buckets, each of size *20* by default. {{{mark(bqti)}}} diverges on the identifier space and the identity binding.

Each node's identifier is a 256-bit value derived by hashing its Ed25519 public key via SHA256, binding the DHT position directly to a cryptographic identity. That key originates from a leaf certificate generated at startup, derived from the hardcoded CA root generated per peer before it attempts a swarm admission. As a result, there is no distinction between the routing key and the authentication key, ensuring that, for the node to take a position along the DHT, it must hold the corresponding private key. Expanding the key space to 256 bits provides higher collision resistance at a 128-bit security level ,replacing SHA-1, whose collision resistance is no longer guaranteed. Beyond that, it naturally aligns with I2P's NetDB, which also organises entries under 256-bit keys (see [[#i2p_network_database][Section 4.X]]).

To determine node proximity, the XOR of two node identifiers is computed byte-by-byte over 32 bytes, yielding a 256-bit distance value in which the leftmost bits carry the most weight. Nodes that share a longer common prefix are considered closer to a given target. For instance, two nodes that differ only in their last bit land in bucket 255, with a nearly identical prefix, and are very close, while two nodes that differ in their first bit land in bucket 0, the maximum distance. As a result, the routing table maintains 256 k-buckets of capacity {{{mark(20)}}}, where higher indices concentrate the local neighbourhood, which are likely to be responsible for storing and serving data. In comparison, lower indices hold the most distant nodes.

The *routing table* holds {{{mark(256 k-buckets)}}}, each with a maximum capacity of {{{mark(20)}}} nodes. Upon attempting to insert a new candidate into a full k-bucket, the oldest node cannot be blindly evicted. If the bucket contains the {{{mark(host node)}}}, it splits at the next bit boundary, and insertion is retried. Otherwise, the oldest node is selected for a liveness probe via a {{{mark(PING RPC)}}} call. If it fails to respond, the candidate is admitted, and the incumbent is evicted. If the probe succeeds, the candidate is discarded.

For the node to be discovered, {{{mark(Kademlia)}}} probes the network iteratively, querying known nodes for their closest neighbours, gradually populating the routing table and gathering more possible solutions to find values in the DHT. In detail, the lookup starts by gathering a set of K locally known nodes closest to the target key, then traverses them. Each iteration dispatches up to α = 3 concurrent {{{mark(FIND\_NODE)}}} RPCs to unvisited candidates, sorted by XOR distance to the target key. Nodes that respond with their own known closest-node set are merged into the candidate set after deduplication. Otherwise, if they fail to respond, they are removed from the possible candidate set and the routing table. Finally, the search terminates when all top-K candidates have been visited, and there are no in-flight RPCs, at which point the candidate set is truncated to the K constant and returned.

*** Stateful RPC on a Stateless Stream Design
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_rpc
:END:

By default, Kademlia over UDP relies on application-level transaction IDs to correlate each request with its matching response, since UDP lacks request-response semantics. At this stage, the current design was built around unidirectional control streams, which inherit the same disadvantage. The sanest solution would have been to open a QUIC bidirectional stream per RPC, letting the transport layer handle the correlation as it sees fit. However, that would introduce pre-request overhead and contradict the established design principle defined at the beginning of the project, which maintained a single outbound control stream per peer for control messages, thereby diminishing stream overhead and latency. Instead, such correlation is handled at the application layer, where every {{{mark(RPC)}}} packet embeds an explicit request identifier, and each in-flight request is registered and identified by that key. When the remote peer's response arrives on its own outbound control stream, the packet identifier is matched against a hash map of pending requests, and the waiting caller is resumed. The trade-off of this approach is a major trade-off is head-of-line blocking within the single shared unidirectional control stream, where a single delayed response stalls all queued requests behind it. Although in practice this is negligible, because these RPC payloads are small and because they go through a single stream, it removes the stream-creation overhead per request and favours better latency than throughput.

*** Network Join
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_network_join
:END:

For a node to be accepted and actively participate in the DHT, it must be admitted by a known bootstrap node, which acts as the entry point to the network. The newcomer first requests the challenge from the bootstrap, which responds with a value derived from the sender's {{{mark(public key)}}}, IP address, a server-side secret salt that rotates every few seconds, and a difficulty target. The joining node must then compute a nonce value such that its hash, combined with its {{{mark(public key)}}} and the received challenge, meets a minimum difficulty target. Once found, it signs the proof with its private key and submits the {{{mark(challenge)}}}, {{{mark(nonce)}}}, and {{{mark(signature)}}} back to the bootstrap for further verification. If the bootstrap accepts the proof, it issues a signed short-lived token granting access to the network. With the token in hand, the joining node performs an iterative lookup against its own identifier, querying for the closest known nodes and progressively widening its range and gradually populating its routing table. At the end of this sequence, the node holds a populated routing table and a valid token that will be used to serve and respond to RPCs as a full participant. Each outbound request embeds the token, and the receiving end verifies it by checking the bootstrap's signature and recomputing the proof, confirming that the requesting node is indeed authenticated.

The token is a self-contained, signed data structure carrying the following fields:

| Field         | Description                                          |
|---------------+------------------------------------------------------|
| {{{mark(swarm\_id)}}}  | Hash of the PGP swarm's public key             |
| {{{mark(issuer\_ca\_cert)}}}  | PGP certificate             |
| {{{mark(issuer\_ca\_cert\_sig)}}}  | PGP signature             |
| {{{mark(trust\_level)}}}  | TEE-based trust level or software             |
| {{{mark(bootstrap\_pk)}}}  | Public key of the issuing bootstrap node             |
| {{{mark(node\_pk)}}}       | Public key of the admitted node                      |
| {{{mark(pow\_nonce)}}}     | Nonce satisfying the proof-of-work                   |
| {{{mark(pow\_challenge)}}} | Original challenge issued by the bootstrap           |
| {{{mark(issued\_at)}}}     | Timestamp of issuance                                |
| {{{mark(expires\_at)}}}    | Timestamp of expiry                                  |
| {{{mark(signature)}}}     | Bootstrap's signature over all preceding fields      |

*** Sybil and Eclipse Attacks
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_sybil
:END:

As depicted in [[#sybil_attacks][Section 2.1.16]], this kind of attack consists of flooding the network with cheap artificial identities to surround a target node and control what it sees. In a similar vein, an eclipse attack is a targeted variant that isolates a specific node by filling its routing table with malicious entries. Additionally, collusion attacks extend both variants by coordinating multiple identity attacks to manipulate the lookup result or selectively withhold data. The primary defence against identity flooding is a *proof-of-work requirement applied at the network join admission*, where each node must solve a computationally hard problem, setting a computational floor on the cost of acquiring a valid identity. As explained in the previous section, {{{mark(bqti)}}} approaches this by finding a nonce that, together with a given {{{mark(challenge)}}} and its {{{mark(public key)}}}, is hashed with the SHA256 function, until its value meets the minimum difficulty set by the entry node. This requirement prevents a node from solving the challenge once and replaying it to register several identities in rapid succession, since each attempt produces a distinct challenge that expires shortly after issuance. Once admitted by the bootstrap, a node receives a signed token with a thirty-minute lifespan. Subsequent RPCs embed this token rather than repeating the proof-of-work, thereby paying the computational cost once per session rather than per message.

The issued token binds the proof to the issuer's public key and challenge, enabling a newcomer to identify the bootstrap that issued it and track its movement on the network. The PKI hierarchy is managed by each swarm, which, upon first boot, generates a PGP keypair and, for each bootstrap node, a signature of its self-signed CA root. The PGP certificate is then distributed to all clients, who load it to enable that swarm. In the current implementation, in addition to PGP signing, TEE attestation, along with the client version, ensures the client is running an unmodified client by checking against a public signed enclave hash matching the client version, as detailed in [[#impl_tee_remote_attestation][Section 4.9.5]]. As a result, this shifts the responsibility for securing and managing the swarm's trust anchor to the swarm maintainer.

With the TEE integration, remote attestation would replace this assumption by removing the dependency on a trusted set of infrastructure nodes, thereby depending on a trusted third party that both guarantees that {{{mark(bqti)}}} sensitive operations are running in trusted hardware and clients are using a valid and trustworthy {{{mark(BitTorrent)}}} client.

*** DDoS Attacks
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_ddos_attacks
:END:

This volumetric attack against a DHT node can exhaust its resources by flooding it with requests, forcing it to process and respond to traffic that it cannot sustain or that is no longer active. To mitigate this issue, two independent solutions are integrated in {{{mark(bqti)}}}. First, a simple rate limiter was integrated with the RPC admission boundary, where every authenticated request carries the sender's cryptographic identity, and the rate limiter tracks request counts per {{{mark(public key)}}} rather than IP address. As a result, even if an adversary rotates the IP address, they cannot bypass the rate limiter tracking table, since the constraint follows the cryptographic identity, not the IP address within the network. Additionally, any sender exceeding {{{mark(100)}}} requests within a {{{mark(60 second window)}}} is automatically rejected until the window resets. Finally, the second mitigation is a bounded store. More precisely,every entry written via {{{mark(STORE)}}} RPCs expires after {{{mark(35 minutes)}}} and is swept every {{{mark(5 minutes)}}}. On top of that, read operations are also guarded lazily, where an expired entry is never served even if the prune cycle has not been triggered yet. When it reaches {{{mark(10 000)}}} entries in total, the oldest entry by insertion order is evicted, guaranteeing that memory consumption is bounded by both time and storage efficiency. Together, these bounds ensure that memory consumption is scoped by both time and capacity, decreasing the impact of sustained flooding attempts.
