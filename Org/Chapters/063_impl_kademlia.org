As introduced in [[#distributed_hash_tables][Section 2.1.9]], BitTorrent's mainline DHT is based on Kademlia. That said, this section details how the concrete implementation diverges from the stock protocol, increased security mitigations applied on top and core decisions made.

*** Routing and Node Identity
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_routing_identity
:END:

# (citeme: Kademlia, read the video to be sure)

According to the paper, stock Kademlia assigns each node a 160 bit identifier derived from SHA1, that identifier will be placed on the Key Space, which is the cluster of 160 k-buckets of size *20* by default. That said, {{{mark(bqti)}}} diverges on the identifier space and the identity binding.

Each node's identifier is a 256-bit value derived by hashing its Ed25519 public key via SHA256, binding the DHT position directly to a cryptographic identity. That key  is originated from a leaf certificate generated at startup, derived from the hardcoded CA root already embedded at compilation time and shared across both QUIC and Kademlia. As a result, there is no distinction between the routing key and the authentication key. Thus, ensuring that in order for the node take position along the DHT it must hold the corresponding private key. Expanding the key space to 256 bits delivers both a higher collision resistance for a 128-bit security level, removing a weaker algorithm whose resistance is no longer guaranteed. Beyond that, it naturally aligns with I2P's NetDB that also organises entries under 256-bits keys (see [[#i2p_network_database][Section 4.X]]).

To determine node proximity, the XOR of two node identifiers is calculated byte-by-byte across 32 bytes, resulting in a 256-bit distance value where the leftmost bits carry the most weight. Nodes that share a longer common prefix are  considered closer to a given target. For instance, two nodes that differ only in their last bit land in bucket 255, nearly identical prefix, very close. While, two nodes that differ in their first bit land in bucket 0, maximum distance. As a result, the routing table maintains 256 k-buckets of capacity {{{mark(20)}}}, where higher indices concentrate the local neighbourhood which are likely to be responsible for storing and serving data, while lower indices hold the most distant nodes.

The *routing table* holds {{{mark(256 k-buckets)}}}, each with a maximum capacity of {{{mark(20)}}} nodes. Upon attempting to insert a new candidate into a full k-bucket, the oldest node cannot be blindly evicted. That said, if the bucket contains the {{{mark(host node)}}}, it is split at the next bit boundary and insertion is retried. Otherwise, the oldest node is selected for a liveness probe via a {{{mark(PING RPC)}}} call. If it fails to respond, the candidate is admitted and the incumbent evicted, otherwise the candidate is discarded.

In order for the node to be discovered, {{{mark(Kademlia)}}} probes the network iteratively, querying known nodes for their closest neighbours, thus populating the routing table slowly gathering more possible solutions to find values on the DHT. In detail, the lookup starts by gathering a set of K locally known nodes closest to a target key, then goes through them. Each iteration dispatches up to α = 3 concurrent {{{mark(FIND\_NODE)}}} RPCs to unvisited candidates, sorted by XOR distance to the target key. Nodes that respond back with their own known closest-node set, which are merged into the candidate set after deduplication, otherwise if they fail to respond back, are removed from possible candidate set and routing table. Finally, the search terminates when all top-K candidates have been visited and there are no in-flight RPCs, at which point the candidate set is truncated to the K constant and returned.

*** Stateful RPC on a Stateless Stream Design
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_rpc
:END:

By default Kademlia over UDP relies on  application-level transaction IDs to be able to correlate each request with its matching response, since UDP does not provide that request-response semantics. At this stage, the current design was built around unidirectional control streams, which inherits the same disadvantage. The sanest solution would have been opening a QUIC bidirectional stream per RPC, letting the transport layer handle the correlation as it see fit. However, that would introduce pre-request overhead and contradicts the established design principle defined at the beginning of the project, which consisted in maintaining a single outbound  control stream per peer for control messages, thus diminishing stream overhead and latency. Instead, such correlation is handled at the application layer, where every {{{mark(RPC)}}} packet embeds an explicit request identifier, and each in-flight request is registered and identified by that key. That said, when the remote peer's response arrives on its  own outbound control stream, the packet identifier is matched against a hashing map of pending request, and the waiting caller is resumed. By adopting this approach, a major trade-off is the head-of-line blocking within the single shared unidirectional control stream, where a single delayed response stalls everything queued behind it. Although, in practice this is negligible, as these RPC payloads are small and by going through one single stream, it removes the stream creation overhead per request and favouring better latency than throughput.

*** Network Join
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_network_join
:END:

In order for a node be accepted and actively participate in the DHT it must be admitted by a known bootstrap node, which acts as the entry point to the network. The newcomer first requests the challenge from the bootstrap, which answers back with a value derived from the sender {{{mark(public key)}}}, IP address, and a secret server-side salt that rotates every few seconds and a difficulty target. The joining node must then compute a nonce value such that its hash, combined with its {{{mark(public key)}}} and the received challenge, meets a minimum difficulty target. Once found, it signs the  proof with its private key and submits the {{{mark(challenge)}}}, {{{mark(nonce)}}}, and {{{mark(signature)}}} back to the bootstrap for further verification. If the bootstrap accepts the proof, it issues signed short-lived token granting access to the network. With the token in hand, the joining node performs an iterative lookup against its own identifier, querying for the closest known nodes and progressively widening its range and slowly populating its routing table. By the end of the sequence the node holds a populated routing table and a valid token, that will be used to serve and respond to RPCs as a full participant. Each outbound request embeds the token, and the receiving end verifies it by checking the bootstrap's signature and recomputing the proof, confirming that the requesting node is indeed authenticated.

*** Sybil and Eclipse Attacks
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_sybil
:END:

As depicted in [[#sybil_attacks][Section 2.1.16]], this kind of attack consists of flooding the network with cheap artificial identities in  order to surround a target node and control what it sees. In a similar fashion, an eclipse attack is a targeted variant, which isolates a specific node by filling its routing table with malicious entries. Additionally, collusion attacks extend both variants by coordinating multiple identity attacks to manipulate the lookup result or selectively withhold data. That said, the primary defence against identity flooding is a *proof-of-work requirement applied at the network join admission*, where each node must solve a complicated problem, setting a computational floor on the cost of acquiring a valid identity. As explained in the previous section, {{{mark(bqti)}}} approach this by finding a nonce that together with a given {{{mark(challenge)}}} and its {{{mark(public key)}}} are hashed with SHA256 function, until its value meets the minimum difficulty set by the entry node. This requirement prevents a node from solving the challenge once and replaying it to register several identities in a rapid succession, since each attempt produces a distinct challenge that expires shortly after issuance. Once admitted by the bootstrap, a node receives a signed token with a thirty minutes lifespan. Then, subsequent RPCs embed this token rather than repeating the proof-of-work, thus paying the computational cost once per session rather than per message.

The issued token binds the proof to the issuer's public key and challenge, making it possible to identify the bootstrap that issued that token to a newcomer and track its movement on the network. Underpinning the PKI hierarchy is a hardcoded CA root certificate in each client, that upon the first boot it generates both the QUIC TLS certificate and the Kademlia Ed25519 leaf certificate, anchoring the node's DHT identity to the certificate. In the current implementation stage, without TEE attestation, the trust CA root is established through the bootstrap and tracker nodes that hold that embedded CA root certificate at compile time. As a result, this shifts the responsibility to the swarm maintainer to secure and manage the swarm's trust anchor.

With the TEE integration, remote attestation would replace this assumption, by removing the dependency on a trusted set of infrastructure  nodes. Thus, depending on a trusted third party that both guarantees that {{{mark(bqti)}}} sensitive operations are running in trusted hardware and clients are using a valid and trustworthy {{{mark(BitTorrent)}}} client.

*** DDoS Attacks
:PROPERTIES:
:CUSTOM_ID: impl_kademlia_ddos_attacks
:END:

This volumetric attack against a DHT node can exhaust its resources by flooding it with requests, forcing it to process and respond to traffic that cannot sustain or no longer is active. To mitigate this issue, two independent solutions are integrated in {{{mark(bqti)}}}. First, a simple rate limiter was integrated with the RPC admission boundary, where every authenticated request carries the sender's cryptographic identity, and the rate limiter tracks requests counts per {{{mark(public key)}}} rather than IP address. As a result, even if an adversary rotates IP address, they can't bypass the rate limiter tracking table, since the constraint follows its identity within the network. Additionally, any sender exceeding {{{mark(100)}}} requests within a {{{mark(60 second window)}}} is automatically rejected until the window resets. Finally, the second mitigation is a bounded store. More precisely, in every entry written via {{{mark(STORE)}}} RPCs expire after {{{mark(35 minutes)}}} and swept every {{{mark(5 minutes)}}}. On top of that, read operations are also guarded lazily, where an expired entry is never served even if the prune cycle has not been triggered yet. When it reaches {{{mark(10 000)}}} entries in total, the oldest entry by insertion order is evicted, guaranteeing that memory consumption is bounded by both time and storage efficiency. Together, these bounds ensure that memory consumption is scoped by both time and capacity, decreasing the impact of sustained flooding attempts.
