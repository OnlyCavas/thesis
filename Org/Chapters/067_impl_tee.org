** Trusted Execution Environment Integration
:PROPERTIES:
:CUSTOM_ID: impl_tee_integration
:END:

*** Enclave Structure
:PROPERTIES:
:CUSTOM_ID: impl_tee_enclave_str
:END:

Until this point the proof-of-concept already presented mitigations for ensuring *Confidentiality* and *integrity* by relying on QUIC's mechanics and implemented software mitigations, alongside the integrations with *I2P* across a SAM bridge providing a way for the user remain anonymous with a swarm. Although, currently there isn't any verifiable trusted way to guarantee an swarm participant is using an actual trust worthy client implementation and actually was him that computed the proof-of-work necessary for swarm admission, between other sensitive operations.

As depicted in [[#impl_tee_integration][Section X.X]], the TEE layer is responsible for providing a way to identify if a peer in fact is authentic, and is running a trustworthy client implementation before admission within the swarm. The integration is structured in two distinct components. The first is the enclave, written in C, running within a Keystone trusted execution environment in complete hardware isolation  from the host operating system. The second is a host-side C++ runner that interfaces with the Keystone SDK, loading, and managing the enclave life cycle. In a similar fashion, the client communicates with the runner through a C FFI layer, allowing Rust to invoke enclave operations without directly depending on Keystone SDK, while ensuring type definitions.

Keystone needs to deploy aggregated components in order for the enclave be able to run within a foreign environment. To simplify deployment the enclave binary along with Eyrie runtime and loader are directly embedded into the {{{mark(bqti)}}} final binary at compile time and later extracted in runtime to a temporary directory on demand. This produces a self-contained binary with all necessary components facilitating its distribution and without needing a separate enclave installation on the target machine. On top of that, it actually solves a major problem with enclave updates and client version matching, by binding a {{{mark(bqti)}}} version to a specific enclave hash, allowing swarm maintainers in a future implementation choose what versions are allowed.

Given to the memory constraints of an enclave environment, not every cryptographic library is suitable. With this in mind, libraries that pre-allocate large buffers or depend on OS primitives are incompatible with the enclave's limited execution model. As a result, {{{mark(TweetNaCl)}}} was integrated for Ed25519 signing as it computes incrementally without pre-hashing, and {{{mark(libtomcrypt)}}} for hashing (SHA256), since Keystone's built-in cryptographic support only covers SHA3. Both libraries are statically linked with the binary along with the Keystone SDK. It is also worth noting that since Keystone's Security Monitor uses Ed25519 with SHA3-512 as the internal hashing function rather than the standard SHA512, the standard Ed25519 verification libraries already integrated are incompatible with the attestation report generated by the Keystone enclave. This required implementing a [[#appendix_keccak_ed25519][custom verifier]] that preserves the Ed25519 curve arithmetic while substituting SHA3-512 as the hash primitive, allowing both software and TEE supported devices to attest TEE peers.

*** Keypair and Sealing Key
:PROPERTIES:
:CUSTOM_ID: impl_tee_kp_sealing_key
:END:

Upon initialization, the enclave derives its Ed25519 key pair deterministically from Keystone's {{{mark(sealing key)}}}, which is the hardware-rooted secret bound to both the enclave measurement and physical device. Consequently, the same binary while running within the same hardware will always produce the same Ed25519 key pair, while any modification to the binary or execution on a different environment will always yield a different key. That said, this stands as the fundamental property that sustains the security model, maintaining its identity across restarts and unforgeable without the exact hardware and binary combination. Crucially, its private key can never leave the enclave, keeping that in mind for each cryptographic operation it is explicitly wiped from enclave memory before returning anything to the host. Thus, taking the necessary security measures to ensure that a compromised host process cannot recover it, and effectively break the trust anchor.

*** Enclave Capabilities
:PROPERTIES:
:CUSTOM_ID: impl_tee_enclave_capabilities
:END:

The current enclave implementation exposes exactly five functions to host from a shared protocol header:

| Header        | Description                                      |
|--------------+--------------------------------------------------|
| {{{mark(OP\_HASH [0x01])}}} | computes a sha256 digest from arbitrary data  |
| {{{mark(OP\_SIGN [0x02])}}} | produces an Ed25519 signature using the enclave's {{{latex(priv\_key)}}} |
| {{{mark(OP\_POW [0x03])}}} | runs proof-of-work computation entirely inside the enclave |
| {{{mark(OP\_FETCH\_PUBKEY [0x04])}}}  | exports the enclave's public key |
| {{{mark(OP\_ATTEST [0x05])}}} | produces remote attestation bounded to a arbitrary nonce |

Each request follows the same structure and life cycle, begins by initialising the enclave, sending the request and awaiting the corresponding typed response via {{{mark(Keystone OCALL)}}}. Once read, destroys the enclave before returning to the host. It is worth noting that the private key is wiped after the end of each life cycle regardless of the operation performed operation.

*** Proof of Work
:PROPERTIES:
:CUSTOM_ID: impl_tee_proof_of_work
:END:

To be sure that the joining peer actually wasted computational power calculating the proof-of-work, when the TEE is enabled that operation was moved within the enclave. It iterates SHA256 over the concatenation of its {{{mark(public\_key)}}}, the received {{{mark(challenge)}}} value, and an incremental {{{mark(nonce)}}} until the resulting hash satisfies the correct number of leading zeros for a given difficulty target. Once the winning hash is found, the result is immediately signed with the enclave's Ed25519 private key and returned back to the host. This approach stands as fundamentally stronger than a software-only proof-of-work, because the signature performed over the hash proves that the computation was actually performed within a trusted environment with a hardware-rooted private key. Notably a software threat actor cannot forge a valid response without the private key, which never leaves the enclave. By relying on TEE for the proof-of-work calculation, proves simultaneously proof of computational effort and proof of hardware authenticity.

Although signing with the enclave's private key would break compatibility with the software certificate system, where each protocol extension generates its own leaf certificate key pair. This is resolved by keeping the enclave's public key constant across generated certificates. As a result, each leaf certificate carries different metadata, but is signed by the same underlying hardware-rooted key, ensuring that the DHT identifier matches the same key that signed the proof-of-work. Thus, making it possible to be later verified by any peer using the peer's DHT identifier, regardless of whether they support TEE or not.

*** Remote Attestation
:PROPERTIES:
:CUSTOM_ID: impl_tee_remote_attestation
:END:

Apart from computational effort, by leveraging TEE remote attestation capabilities is possible to guarantee that a remote peer is trustworthy without needing a PKI in place. The attestation report generated by Keystone is composed of three-layer chain of trust rooted in the device hardware. The first layer is the *Security Monitor* report, which contains the measurement hash and public key, signed by the own device's hardcoded hardware key using Keccak-Ed25519. The second layer is the *Enclave Report*, containing the {{{mark(enclave\_hash)}}} reflecting the enclave immutability, if the code is modified so will the hash. Followed by the caller-supplied {{{mark(nonce)}}} embedded as the report data, on the proof-of-concept case is the computed proof-of-work, signed by the *Security Monitor*. The final layer, is the enclave's {{{mark(device public key)}}} itself, embedded as the trust anchor at the root of the chain.

In light of the above, the verification process follows the reverse layer verification. Starting by matching the {{{mark(dev\_pub\_key)}}} with the enclave's trusted key, which is distinct for each device once in production. After that, the *Security Monitor Signature* must be valid under that same {{{mark(dev\_pub\_key)}}}, along with the *Enclave Signature* be valid with the *SM Key*. Once verified, optionally the enclave hash can be compared against a hardcoded expected value to confirm whether the enclave code has been modified, and guarantee that the factory code is running within the TEE, which is optimal for detecting any tampering with the enclaves binary. At last, the embedded nonce in the report data is verified against the real nonce supplied by the challenger, preventing a threat actor from replaying a intercepted valid report.

That said, an enclave trust anchor relies on the {{{mark(device public key)}}}, however in the current implementation this is intentionally relaxed, having it hardcoded or even ignored. For instance, in a production environment deployment, the device key would need to be signed by a centralized third party authority, similar to how Intel SGX and TDX rely on Intel's attestation service, contradicting the initial statement of achieving a proof-of-concept ({{{mark(bqti)}}}) entirely decentralised. That said, to avoid this dependency, instead the trust anchor lies on {{{mark(a public manifest file)}}}, currently with the following structure:

#+begin_src json
[
  {
    "version": "0.1.0",
    "enclave_hash": "4855bd98e..."
  }
]
#+end_src

As a result, each {{{mark(bqti)}}} version ships with a matching {{{mark(enclave\_hash)}}} exposed on a signed manifest, with the developer private key, which never leaves the device, effectively binding it with a enclave measurement. Hence, peers verify the enclave hash from the report attestation against the manifest rather than the hardware certificate chain, preserving full decentralisation where any user can manually verify and attest the enclave measurement.

It is worth acknowledging that this approach doesn't remove the third-party trust entirely, only shifts it from a hardware manufacturer to a project maintainer. Although, unlike Intel's attestation service, the manifest is publicly auditable and the enclave hash is independently reproducible by anyone building it from source, making the trust assumption transparent and verifiable by anyone. Additionally, enabling a swarm maintainer on a future version establish swarm admission requirements, having enough information to decide which {{{mark(bqti)}}} versions are allowed, or whether TEE is mandatory.

Nonetheless, this approach carries its own attached risks. Recent supply chain attacks have targeted developer's signing keys as a viable attack vector. Taking by example the node packaging ecosystem, where highly interdependent dependency trees make it possible for a single compromised package to propagate malware across thousands of downstream consumers as legitimate software. Similarly, a compromised developer signing key would allow pushing a malicious enclave hash measurement as a trusted version, silently breaking the trust anchor. Despite remaining as an open problem and known limitation of a developer-signed trust model in general, similar models like Linux package signing address this partially through PGP key revocation, but ultimately the strongest mitigation is transparency. Meaning, open source code means the enclave hash is independently reproducible by anyone, making its silent substitution detectable and extremely hard to break.

*** Backend Abstraction and Feature Flag
:PROPERTIES:
:CUSTOM_ID: impl_tee_abs
:END:

With the objective of keeping the client as modular as possible and avoiding binding it to a specific TEE implementation, TEE support is optional at compile time via the {{{mark(--features tee)}}} compilation flag. Without it, a client falls back to software-only authentication transparently, with no code changes required. This approach compiles only the necessary operations into the binary. Furthermore, depending on the target processor architecture, a different TEE backend is compiled: RISC-V {{{Keystone}}} and ARM {{{mark(OP-TEE)}}}.

In order to support both backends under the same API, all enclave operations are accessed through the {{{mark(TeeExecute)}}} trait, defining the four attestation methods: {{{mark(proof-of-work)}}}, {{{mark(signing)}}}, {{{mark(public key retrieval)}}}, and {{{mark(attestation)}}}. This is complemented by the same abstraction pattern for the certificate integration, which is defined by {{{mark(ActiveKeyIdentity)}}} which changes with its corresponding compilation feature, switching its underlying behaviour. Finally, the report attestation is carried by a default enum that specifies the attestation type: {{{mark(KeystoneReport)}}}, {{{mark(OPTeeReport)}}}. Upon bootstrap admission, a verifying peer verifies a report attestation differently depending on the report type, having a concrete implementation for both baked into the {{{mark(bqti-tee)}}} library, which acts as a middle ground between the {{{mark(FFI)}}} and {{{mark(bqti)}}}.

*** Identity Integration
:PROPERTIES:
:CUSTOM_ID: impl_tee_identity
:END:

In similar fashion, TEE is integrated through the same {{{mark(KeyIdentity)}}} abstraction layer used by the software certificate path. When compiled with TEE support, {{{mark(TeeKeyIdentity)}}} replaces the software implementation, silently delegating QUIC TLS signing to the enclave, without changing any aspects at the transport layer. As already established in [[#impl_kademlia_routing_identity][Section X.X]], node identity is derived from the original certificate, which in TEE case is generated from the enclave public key, and then repeated across all protocol layers. With TEE enabled, that key is hardware-bound, elevating the same single key design from a software-only assumption to a hardware guarantee.
