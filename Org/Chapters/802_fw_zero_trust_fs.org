** Zero-Trust filesystem (bqti-FS)
:PROPERTIES:
:CUSTOM_ID: fw_zt_fs_bqti
:END:

The BitTorrent hardware-rooted implementation developed throughout this thesis lays the groundwork for a broader application: a fully decentralised, zero-trust distributed filesystem, referred to henceforth as {{{mark(bqti-FS)}}}. Whereas conventional cloud storage, such as *OneDrive* or *GoogleDrive*, entrusts user data to a centralised provider, {{{mark(bqti-FS)}}} brings a decentralised alternative where all user data resides, encrypted, scattered among other participants' machines, and can only be decrypted within the TEE under the user's exclusive control. The existing {{{mark(bqti)}}} stack: QUIC transport, I2P anonymity, and TEE attestation, would serve as the underlying transport and trust fabric, with storage organised as private swarms scoped by a maintainer's PGP-signed certificate.

{{{figure(diagrams/future_work/bqt-fs.pdf, Conceptual trust topology of bqti-FS: untrusted WASM client\, trusted TEE device (key vault and DHT identity)\, and a swarm storing encrypted user data\, over QUIC/I2P.)}}}

In this architecture, a TEE-capable device would act as the user's root of trust and key vault, holding the hardware-sealed key that never leaves the device. In the current implementation, the hardware-sealed public key is the DHT identity of a TEE-based peer, and a {{{mark(info\_hash)}}} identifies a torrent across a BitTorrent swarm. Considering the device as the sole credential within the network and the user's identity within the swarm eliminates the need for password-based authentication. Therefore, the TEE-based device could serve as both a cryptographic key and an identity key within a private swarm, relying on the TEE public key as the identifier, along with PoW and PoR mitigations.

Building on this idea, consider a scenario in which the user accesses their swarm identity from an untrusted device. A WebAssembly application, loadable on any machine, could serve as a sandbox to visualise and modify any distributed data. The WASM application would establish a secure channel to the user's trusted device and rely on DRM-inspired progressive decryption using ephemeral key material streamed from the TEE device. As a result, the untrusted device can render small portions of data, decrypt each portion only when necessary, and wipe it after utilisation. This execution model aligns with runtimes such as *WATZ* ([[#watz][Section 2.3.9]]), enabling WASM applications to run within TrustZone's Secure World with remote attestation, thereby ensuring that the DRM logic executes in a hardware-enforced trusted environment.

Several existing systems address decentralised storage, each with distinct limitations:

+ *Filecoin* {{{citep(filecoin)}}}:

  A decentralised storage network that uses cryptographic proofs and economic incentives to ensure peers reliably host data, without providing any *confidentiality* or *hardware-root trust*.

+ *Tahoe-LAFS* {{{citep(tahoe)}}}:

  A zero-knowledge distributed filesystem that encrypts and erasure-codes data before distributing it across storage nodes. However, its trust is software-based and therefore doesn't support either *hardware-rooted trust* or *anonymity*.

+ *Sia* {{{citep(sia)}}}:

  A blockchain-based decentralised marketplace storage platform where users rent storage from hosts via smart contracts and must periodically submit cryptographic storage proofs. However, these keys reside only on the client machine, without any hardware-rooted protection, meaning a compromised device could expose all user data.

Even though these solutions provide a decentralised file storage, none combine the three properties that {{{mark(bqti-FS)}}} idealises: *confidentiality*, *TEE attestation*, and *network-level anonymity*. Some solutions, such as *Filecoin* and *Sia*, rely on a blockchain-based storage mechanism to motivate users through economic incentives, but expose user data publicly and lack a hardware-root trust model. Additionally, *Filecoin* is a layer on top of IPFS, a content-addressed filesystem similar to BitTorrent but without an incentive mechanism to promote file distribution and ensure fairness with the swarm. Tahoe-LAFS comes closest, achieving confidentiality through client-side encryption, but its trust model is entirely software-based and offers no remote attestation or anonymity. {{{mark(bqti-FS)}}} would distinguish itself by binding storage identity and decryption authority to a hardware enclave, with the option to route its traffic through I2P, while remotely attesting peers. Additionally, considering the reputation system proposed in [[#fw_protocol_reputation][Section 6.2]], rather than relying on blockchain-based incentives, it would leverage swarm policies to ensure every peer contributes back to the network. Since every swarm controls its own trust anchor (PGP), a swarm could enforce a set of policies admitting only TEE-attested peers and rewarding reliable hosting, building on the underlying BitTorrent over QUIC implementation to promote fairness and content distribution rather than a financial ledger.

Although {{{mark(bqti-FS)}}} would, in theory, protect in-transit data and private keys, while guaranteeing safe preview with DRM-inspired progressive decryption with ephemeral key material, it cannot fully defend against a compromised host once data is rendered on its physical display, which is a known vulnerability of DRM software. Within these bounds, {{{mark(bqti-FS)}}} could guarantee confidentiality of data in transit and at rest, as well as the integrity of the execution environment. The choice of {{{mark(RISC-V)}}} for the proof-of-concept was motivated by this trajectory, leveraging an open and auditable hardware base that provides a root of trust without relying on a single vendor's attestation service. RISC-V is widely used in IoT devices and microcontrollers, which could broaden the applicability of this approach.
