** BitTorrent Protocol
:PROPERTIES:

:END:

*** Protocol
:PROPERTIES:
:CUSTOM_ID: impl_bep_protocol
:END:

As explained in [[#torrent_specification][Section 2.1.1]], the BitTorrent wire protocol governs how peers negotiate availability and exchange piece data.

The connection process begins when an interested peer sends a handshake message containing both the torrent's {{{mark(info\_hash)}}} and {{{mark(peer identification)}}} (typically obtained via DHT), which the receiving counterpart validates before proceeding. If they are valid, both sides complete the handshake by acknowledging each other, establishing a channel for further protocol exchange. Each peer broadcasts its bitfield, a compacted bitmap indicating which pieces it currently holds, for an agreed {{{mark(info\_hash)}}}, allowing both sides to determine whether the counterpart has anything of interest.

From that point forward, piece exchange becomes a simple four-state pipeline, exchange the following states ({{{mark(interested)}}}, {{{mark(not\_interested)}}}, {{{mark(unchoked)}}}, {{{mark(choked)}}}). A peer signals {{{mark(Interested)}}} when a remote holds a piece that it needs. The remote may respond with {{{mark(Unchoke)}}} to grant upload permission, or {{{mark(Choke)}}} to withhold data. Once {{{mark(unchoked)}}}, the requesting peer establishes a request pipeline, issuing up to *128 concurrent block requests*. Depending on the piece size defined by the torrent metadata file, being the default {{{mark(piece\_size)}}} of 512 kilobytes, this typically translates to requesting approximately *4 to 5 concurrent pieces* at a time. Each request is selected sequentially from the difference between the remote's bitfield and the local peer's bitfield (e.g., pieces the remote has that the local still needs). As each block arrives, it is validated and processed, and the pipeline is immediately refilled with new requests to keep the bidirectional stream fully saturated. If a peer is choked, all pending requests are cleared, and the pipeline drains until the remote unchokes again.

As described earlier, the current *BEP router implementation* relies on a long-lived unidirectional *shared control stream* for handling the following messages: {{{mark(handshake)}}}, {{{mark(bitfield)}}}, {{{mark(unchoke)}}}, {{{mark(choke)}}}, {{{mark(interested)}}} and {{{mark(not\_interested)}}}. However, to maximise throughput, it dispatches several *bidirectional concurrent data streams*, while respecting the BitTorrent protocol specifications, ensuring no more than 5 concurrent pieces are streamed to another swarm participant.

It is worth noting that the current implementation requests pieces sequentially rather than using more advanced strategies, described in [[#bt_rarest_first_sota][Section 2.1.X]], such as {{{mark(rarest-first)}}}, {{{mark(endgame mode)}}}, or {{{mark(optimistic unchoking)}}}. The current design prioritises simplicity and a stronger focus on the security aspects of the BitTorrent protocol over a full feature implementation of a BT client. Nevertheless, it remains a fully functional BitTorrent proof-of-concept client, supporting multi-peer connections, concurrent multi-downloads, and seeding, while incorporating several mitigations against common attacks targeting real-world clients.

*** Piece Substitution Mitigation
:PROPERTIES:
:CUSTOM_ID: impl_bep_piece_subs
:END:

While piece data is travelling over the wire, a malicious peer can poison a download by serving pieces whose content does not match the torrent metadata, or by sending different pieces for the requested index, thereby corrupting the file or stalling the download progress. A possible mitigation is that every piece sent by a seeder would have to be signed before transmission and then verified by the receiver, ensuring that the piece's data hasn't been tampered with. Although signing the data alone would not suffice, for example, an attacker could serve valid data with a different index. Including the piece index in the digest binds the signature to both the piece content and position. For this reason, a seeder computes an SHA256 digest over the concatenation of the piece index and its corresponding data, i.e. {{{mark(sha256( index | piece\_data ))}}}. Then signs the result with its *Ed25519* private key, appends its 64-byte signature to the final payload, and sends it over the wire.

Once received by the downloader, it extracts the signature from the last 64 bytes of the payload and verifies the signature against the seeder's public key before accepting the piece. Since the signing key is the same one that anchors the node's DHT identity, a fraudulent piece can be traced to the corresponding seeder, which could be leveraged in future work to detect and downgrade its reputation. After verifying the signature, the same hash is computed on the downloader side using locally known information {{{mark(sha256(local index | remote piece\_data))}}}. If both hashes match, the piece is accepted and verified against the torrent metadata file, which computes the hash of that data and compares it with the metadata's piece hash table. This ties piece integrity back to the identity model already established in [[#impl_kademlia_routing_identity][Section 4.4.1]].

*** I/O operations
:PROPERTIES:
:CUSTOM_ID: impl_bep_io_operations
:END:

After each piece is successfully verified against its corresponding hashing function in the torrent metadata (which may depend on the torrent file version), it is marked as complete and written to disk. A naive implementation for persisting data would buffer the bytes as pieces arrive in memory and write the complete file to disk only once, after all pieces have been downloaded. Consequently, this approach would lead to a higher memory demand and potentially cause a crash, despite being acceptable for smaller files. To mitigate this, the client adopts different strategies depending on its current state.

At the *downloading state* before the session initiates any connection with a possible peer, it begins pre-allocating disk space and pre-creating the directories and files necessary, consulting the torrent metadata and caching the corresponding file pointer. As pieces start to arrive and are successfully accepted by the security measures, they are forwarded to the writer, which writes them to their file position according to their offset and length, until the last piece arrives. Once all files are successfully written, the file handler is dropped and the session's internal state shifts to *seeding*. This approach ensures the downloader can download a large quantity of data, and the client handles it accordingly, storing only the file pointer for further interaction. Pre-allocating the correct file structure reduces overhead during downloads by focusing on writing small portions of each file each time.

All session data is stored in a dedicated internal directory, organised by torrent identity (e.g., {{{mark(info\_hash)}}}). For each active downloading session, the client pre-creates a directory at {{{mark(\$HOME\//.local\//share\//bqti\//downloads\//<info\_hash>\//)}}} containing the downloaded data, alongside the original {{{mark(.torrent)}}} metadata file and most importantly a {{{mark(.bqtiresume)}}} file responsible for tracking the current bitfield state. By establishing this structure, the client can perform the respective download within its protected environment, keeping itself contained per torrent. Thus, storing, managing session cache data, and ensuring cleanup is straightforward without risk of collisions between concurrent downloads and user-managed directories. It is also worth mentioning that when the download finishes, the client notifies the user and creates a soft link named *download* pointing to the download's internal location for easy user access. This feature was inspired by {{{cite(nix_ref)}}}, which takes a similar approach by letting users get the compiled result within its internal structure.

In a similar fashion, at the *seeding state*, the implementation follows the same strategy for performance reasons. Rather than repeatedly opening individual files or the full set of files for every incoming piece request from remote peers, which would translate to a high overhead and slow performance. The client opens all files once at session start and maintains their file pointers in memory for the entire session, allowing fast, low-overhead data serving. However, this approach has a major flaw: if a user renames, moves or modifies a shared file externally during the session, the cached file pointers become invalid, potentially resulting in read failures or corrupted data being served to other peers.

To solve this without introducing additional overhead, the client creates hard links pointing to the original files before reading any data from disk. Hard links are just directory entries pointing to the same inode, which means very low memory cost, no copy overhead, and no performance drawbacks. These links are stored in the same dedicated internal directory (for example, on Linux: {{{mark(\$HOME\//.local\//share\//bqti\//uploads\//info\_hash\//)}}}). As a result, even if the user renames, moves, or modifies the original file, the client continues to access the data safely through the hard links, unaffected by external changes. Similarly, the seeding directory mirrors the same structure, storing hard links to the original files, a {{{mark(.bqtiresume)}}} file that tracks the verified piece state to avoid re-verification on restart, and the original {{{mark(.torrent)}}} metadata file.

*** Session Management
:PROPERTIES:
:CUSTOM_ID: impl_bep_session_management
:END:

As explained in the previous section, a torrent session occupies one of four states during its lifespan, without persisting internal data across transitions: {{{mark(Idle)}}}, {{{mark(Downloading)}}}, {{{mark(Seeding)}}}, or {{{mark(Cancel)}}}. Upon creation, a session always begins in the *idle state*, then transitions to the appropriate state based on the requested session purpose. Unlike all the other states, the *idle state* acts as a neutral transition state, the only one capable of preserving the last known state and its data. This choice was motivated by the need to implement a pausing system that allows the session to transition to a stale state without losing the progress made in the previous one. From *idle state*, a session can transition to *downloading state*, where the node starts sending {{{mark(Interested)}}} requests to already-known swarm participants, or directly to *seeding state*, where it verifies its local data and starts serving.

{{{figure(diagrams/065/state_machine.pdf, Torrent session state machine with transitions between Idle, Downloading, Seeding, and Cancelled states.)}}}

Once in the *download state*, the session will try to start and complete the download, naturally transition to the *seeding state* once it finishes, without returning to the *idle state*. Either active state (*download*, *seeding*) can be paused back to *idle state*, while presenting progress through the persisted bitfield, or can be cancelled irreversibly, transitioning to its final state *cancel state*. Cancel state is a terminal state with no recovery path, optionally purging downloaded data.

Building on this, a session is created once and held active for the entire client lifespan until explicitly cancelled. Each session is responsible for managing its own state and independently driving peer discovery. Upon starting the session, it reads the bootstrap nodes embedded in the {{{mark(.torrent)}}} metadata and attempts to join the swarm via the DHT. From that point forward, peer discovery runs continuously on independent intervals: *querying the DHT for known peers*, *falling back to PEX gossip* for public torrents, and *announcing* the torrent to the DHT when in *seeding state*. In case DHT query returns no peers, the peer discovery mechanism enters a rebootstrap loop until it finds new peers, ensuring recovery from transient network partitions without requiring user intervention.

To expedite discovery and speed up the joining process for newly added torrents, all sessions share a common set of known peers. As a result, if one session discovers new peers for a specific {{{mark(.torrent)}}}, all sessions acknowledge them and try to establish a BEP connection by exchanging bitfields. As there is only a single QUIC connection per peer, it is not necessary to establish a new connection, only to set up a BEP channel.

** IPC server/Client
:PROPERTIES:
:CUSTOM_ID: impl_ipc
:END:

From the very beginning, the design philosophy of this proof-of-concept has been to emulate a real BitTorrent client as faithfully as possible. Because of this, *seeding* and *downloading* operations are delegated to a background daemon, allowing them to run independently of any user interface. By default, the client ships with a dedicated CLI interface that interacts with the running daemon to start, monitor, and manage torrents.

Both communicate through a Unix domain socket bound at {{{mark(\//run\//user\//bqti\//\{instance\}.sock)}}}, and only accessible to the owning user via {{{mark(0o600)}}} permissions. To avoid type duplication across binaries and to define a common API for future client implementations besides the default CLI, all definitions and types are isolated in a dedicated {{{mark(bqti-ipc)}}} lib crate. Both the daemon and CLI consume this as a common dependency. For the simple, fast exchange of messages through the virtual wire, it relies on the JSON format, making it easier to parse messages.

Once the CLI connects to the running daemon, it sends a single serialised request, reads the response, displays it, and disconnects. The CLI command availability covers expected lifecycle operations, such as adding a *download* or *seed*, pausing, resuming, removing a specific torrent by identifier, listing active torrent sessions, querying live status, and requesting a graceful shutdown. The exception to this default behaviour is the {{{mark(EventStream)}}} command, which upgrades the connection into a persistent event stream rather than closing after a single response. When a new client connects, the server begins by replaying a full snapshot of all active torrents and their state before forwarding live events, thereby preventing it from missing state that accumulated during its runtime.

From that point forward, the client starts by receiving a continuous feed of typed events formatted in JSON: {{{mark(TorrentAdded)}}}, {{{mark(SessionStateChanged)}}}, {{{mark(DownloadCompleted)}}}, and many more to keep the client interface always updated with the current backend state. During the event stream, the CLI renders a simple, meaningful TUI that presents the current state of each active torrent session to the user. For instance, for a *downloading torrent*, it reports the current and total pieces alongside the download rate, while during a *seeding torrent* it reports the upload rate and the connected peer count.

In case a client falls behind the broadcast buffer, it will eventually receive an error and can reconnect cleanly. All things considered, the event stream pattern was inspired by the {{{mark(niri's)}}} compositor's {{{gls(ipc)}}} architecture, which essentially follows the same snapshot-stream approach for managing window manager state with external clients {{{cite(niri_ref)}}}.

Overall, despite relying on a hardcoded socket destination, the design still supports several concurrent daemon instances per user by varying the {{{mark(BQTI\_INSTANCE)}}} environment variable, which changes the underlying socket path. This approach proves its usefulness in isolated testing environments and running parallel instances.
