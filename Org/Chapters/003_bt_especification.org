*** Torrent File Format and Specification
:PROPERTIES:
:CUSTOM_ID: torrent_specification
:END:

Before any peer can join the *swarm* (the group of peers sharing a specific file or set of files), it needs to know how to interact with the *BitTorrent* network and locate the desired content. To achieve this, it relies on a *metadata file* also known as *.torrent*. The *.torrent* file is encoded using *bencoding*, a simple, binary-safe serialisation format designed specifically for BitTorrent. It supports four data types:

  + byte *strings*, which are length-prefixed base ten, separated by a colon and the value. Like: 4:spam:corresponds

  + *integers*, that are represented by an *'i'*, then by a number in base 10, followed by an 'e'. Like: *'i3e'*

  + *lists*, that resembling the previous ones, are represented by an *'l'* followed by the respective elements encoded also in *bencoding*. Like: l4:spam4:eggse

  + *dictionary*, these are encoded by an initial *'d'* followed by the list of alternating keys and their respective values. Like: d3:cow3:moo4:spam4:eggse

The entire manifest file is a single *bencoded dictionary* containing the essential information about the swarm, which includes:

*Metadata* about the shared file(s):

  + *Announce*: it holds the URL of the tracker

  + *Info*:

    + *name*: UTF-8 encoded string, that normally stores the name of the file(s) or directory. But it is only visual

    + *piece length*: a map to the number of bytes per piece. Normally, files are split into fixed-size chunks for download in a stream. This section holds the fixed size for each piece, except for the last, which may be truncated. Its value is almost always $2^{18}$ = 256 KB.

    + *pieces*: it's a map that records the chunk's SHA-1 hash, which corresponds to the index. This facilitates both identifying and retrieving the pieces within the swarm and verifying the integrity of the file(s).

    + *length*: this key is used only when the download is a single file. Also, it maps the file's length in bytes

    + *files*: in case there is more than one file, this key is used.

    + *path*: it represents a list of UTF-8-encoded strings that correspond to subdirectory names, with the last one being the actual filename, a *zero-length* list represents an error.

Taking a deeper insight into BitTorrent's *peer protocol*, it operates over *TCP* or *uTP*. Also, peer connections are *symmetrical*, meaning that *messages* sent in both directions look the same. The peer protocol checks the lookup table in the metadata file *.torrent* and selects pieces by their index, starting at zero. When one finishes downloading a piece and checks that the hash matches, it then announces it to its peers.

*** uTP (UDP Tracker Protocol)
:PROPERTIES:
:CUSTOM_ID: utp_tracker
:END:

BitTorrent clients typically communicate with trackers using HTTP over TCP, following the specified *Peer Discovery Mechanism* available in the *metadata file* (.torrent). However, this approach isn't ideal and brings significant protocol overhead.

At the Ethernet layer, each packet carries about 14 bytes of overhead; at the IP layer, about 20 bytes; at the TCP layer, about 20 bytes; and then an additional overhead at the Application Layer (HTTP). For example, a typical request and response, such as a tracker query to return a list of peers, {{{citep(bt_002)}}} requires about 10 packets and roughly 1206 bytes in total.

Switching over to a UDP-based protocol will substantially decrease overhead. As a UDP tracker protocol, it uses only 4 packets and approximately 618 bytes for a similar operation, thereby reducing overall traffic volume by about 50%. For individual clients, this saves roughly 1 KB per hour, which is almost nothing. However, as *trackers* serve millions of peers, they manage a load reduction of about 50%, highly improving performance per peer.

Moreover, a *UDP-based* protocol doesn't require connection establishment, teardown, or complex parsing of HTTP headers. This approach simplifies tracker implementation, requiring less code, reducing CPU and memory demands, and improving overall performance and scalability. On the other hand, UDP is an unreliable, connectionless protocol that lacks built-in retransmission of packets and congestion control features, which are present in TCP. Because of this, the application layer must implement these features itself and audit the reliability and fairness of bandwidth sharing.

*** Connection State
:PROPERTIES:
:CUSTOM_ID: connection_state
:END:

Each connection contains two bits of state at either end {{{cite(bt_001)}}}:

  + *Choked*: Notifies the remote peer of the end of the data stream until further unchoking occurs. Data transfer occurs only when one side is interested, and the other is not choking.

  + *Interested*: Tracks whether a peer actually wants pieces from its connected neighbour. A leecher must maintain a lack of interest whenever it doesn't have anything to request from a remote peer, even when in a choked state. Therefore, allowing remotes to quickly detect which neighbours will begin leeching immediately after unchoking.

Once a peer initiates a connection, it defaults its inner state to choked and uninterested. Then, after connecting to a remote peer and receiving an unchoke, it loads the pipeline with missing pieces, thereby optimising the underlying transport-layer performance. On the other hand, requests that can't be written to the TCP buffer immediately should be queued in memory rather than kept in an application-level network buffer. So they can all be thrown out when a choke happens.

*** Rarest First
:PROPERTIES:
:CUSTOM_ID: bt_rarest_first_sota
:END:

BitTorrent motivates peers to keep contributing to the network and maintain overall reciprocity within the swarm through several key mechanisms, one of which is the {{{gls(rf)}}} piece selection strategy {{{citep(bt_001)}}}.

In the BitTorrent protocol, when selecting pieces for the next request, peers often prioritise the *rarest piece* among their connected neighbours, typically the piece held by the fewest peers in their local cluster within the swarm. Moreover, the "local rarest first" approach has several benefits. Ensuring that peers can acquire unique or uncommon pieces, allowing them to upload them later back to the network and propagate these rare pieces further, thus improving overall reciprocity chances.

By spreading rare pieces more efficiently, it reduces the likelihood that a single piece becomes unavailable, thereby mitigating the risk that a seeder departs from the swarm. Also, common pieces are deferred until later to prevent redundant downloads from the seeder and to allow it to propagate more chunks to more leechers efficiently.

In swarms with increased constraints, imbalance due to a low quantity of seeders and a high amount of leechers, the rarest-first algorithm significantly outperforms naive sequential or random peer selection. When many leechers concurrently request the same piece from the seeder, redundant transfers occur, wasting resources. Instead, the rarest-first algorithm tries to motivate peers to fetch different pieces from other peers, thus further distributing the load among low-consumption seeders.

This approach is paramount when the original seeder goes offline, leaving the torrent in an uncertain state where a swarm may lack the pieces needed to complete a file download, rendering it irrecoverable. Therefore, *Rarest First* mitigates this by aggressively replicating the scarcest pieces first, thereby minimising the risk of piece loss and substantially enhancing swarm scalability.

To solve this issue, a client initially selects random pieces until at least one full piece is completed. In some implementations, 4 pieces are chosen randomly. Once a peer has something to offer, it switches back to the standard rarest piece implementation. Therefore, solving the issue when a peer has no pieces yet, which blocks him from uploading to the network, prevents him from benefiting from reciprocity. Hence, this algorithm promotes piece diversity within the swarm, reduces dependence on seeders, and distributes the scarcest pieces to additional peers, greatly improving swarm robustness and scalability.

*** End Game Mode
:PROPERTIES:
:CUSTOM_ID: bt_end_game_sota
:END:

In the BitTorrent download process, towards the very end, a common problem arises: the last few missing sub-pieces are commonly requested by slower peers. As a result, it can cause significant delays in the download process, potentially blocking the ongoing data transfer, affecting performance, and degrading the overall network. The longer it takes to become a seeder, the more this cyclical pattern spreads across the swarm, slowing down all operations.

Some BitTorrent clients prevent this issue by activating the *End Game Mode* when all remaining sub-pieces are already being requested. This mode prevents bottlenecks by aggressively sending duplicate requests for every remaining sub-piece to all known peers that might have it. Hence, creating a flood of requests to ensure the client can obtain the final pieces from whoever delivers them first. However, this solution consumes excessive bandwidth and may clog other peers.

Taking this into account, as soon as a sub-piece arrives from any peer, a client immediately cancels all duplicate requests for the same sub-piece from other peers. Actually, the protocol relies on BitTorrent's "cancel" message to honour this approach.

Almost all modern clients already implement this behaviour by default, where the sources {{{citep(bt_001)}}} suggest *mainline BitTorrent*, *libtorrent*, *Transmission*, *qBittorrent*. Moreover, they present empirical measurements that effectively demonstrate that it significantly reduces latency with minimal noticeable overhead.

BitTorrent employs a choking algorithm based on a variant of the {{{gls(tft)}}} from repeated game theory {{{citep(bt_001)}}}. Peers maintain a fixed number of unchoke slots, prioritising neighbours that contribute the most upload bandwidth in return.
