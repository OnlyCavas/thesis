*** Torrent File Format and Specification
:PROPERTIES:
:CUSTOM_ID: torrent_specification
:END:

Before any peer can join the *swarm* (the group of peers sharing a specific file or set of files), it needs to know on how to interact with the *BitTorrent* network and locate the desired content. To achieve this, it relies on a *Metadata File*, that is also known as *.torrent*. The *.torrent* file is encoded using *Bencoding*, a simple, binary-safe serialization format designed specifically for Bit Torrent. It basely supports four data types:

  + byte *strings*, which are length-prefixed base ten, separated by a colon and the value. Like: 4:spam:corresponds

  + *integers*, that are represented by an *'i'*, then by a number in base 10, followed by an 'e'. Like: *'i3e'*

  + *lists*, that resembling the previous ones, are represented by an *'l'* followed by the respective elements encoded also in *bencoding*. Like: l4:spam4:eggse

  + *dictionary*, these are encoded by an initial *'d'* followed by the list of alternating keys and their respective values. Like: d3:cow3:moo4:spam4:eggse


The entire metadata file is a single *bencoded dictionary* containing the essential information about the swarm, which includes:

*Metadata* about the shared file(s):

  + *Announce*: it holds the URL of the tracker

  + *Info*:

    + *name*: UTF-8 encoded string, that normally stores the name of the file(s) or directory. But is only visual

    + *piece length*: it's a map to the number of bytes in each piece. Normally, files are split into fixed-size chunks in order to be downloaded in stream, this section holds the fixed-size for each piece, with the exception of the last that may be truncated. Its value is almost always, 2 ^ 18 = 256 K.

    + *pieces*: it's a map that keeps record of the chunk SHA-1 hash, that corresponds to the index. This facilitates both pieces of identifying and fetching the pieces inside the swarm, and to verify the integrity of the file(s).

    + *length*: this key is only used, when the download is one file. Also, it maps the length of the file, in bytes.

    + *files*: in case of be more than one file, this key is used.

    + *path*: it represents a list of UTF-8 encoded strings that corresponds to subdirectories names, which the last is the actual filename. Which means that a *zero length* list represents an error.


Taking a deeper insight inside of Bit Torrent's *peer protocol*, we can observe that it operates over *TCP* or *uTP*. Also, peer connections are *symmetrical*. Which means, that *messages* sent in both directions look the same. The peer protocol checks the look up table stored inside of the metadata file, *.torrent*, and selects the pieces by their index, starting at zero. When one finish downloading a piece and checks that the hash matches, it than announces it to its peers.

*** uTP (UDP Tracker Protocol)
:PROPERTIES:
:CUSTOM_ID: utp_tracker
:END:

BitTorrent clients typically communicate with trackers using HTTP over TCP, following a specified *Peer Discovery Mechanism*available on the *metadata file* (.torrent). However, this approach isn't ideal and brings significant protocol overhead.

# (citeme: utp 010)

At the Ethernet layer, each packet carries about 14 bytes of overhead, at IP layer about 20 bytes, at the TCP layer about 20 bytes and then an additional overhead at the Application Layer (HTTP). For example, a typically request and response, like a tracker queries to return a list of peers, accordingly [cite] requiring about 10 packets and roughly 1206 bytes in total.

By switching over to a UDP-based protocol will substantially decrease overhead. As a UDP tracker protocol, uses only 4 packets and approximately 618 bytes for a similar operation, thus achieving a reduction of about 50% in overall traffic volume. For an individual clients, this ends up saving roughly 1 KB per hour which is almost nothing. However, as *trackers* serve millions of peers, then manage a load reduction of about 50%, highly improving performance per peer.

Moreover, a *UDP based* protocol doesn't need connection establishment, tear down, and complex parsing of HTTP headers. This approach simplifies tracker implementation, requiring less code, reduces CPU and memory demands, and improves overall performance and scalability. On the other hand, UDP is an unreliable, connectionless protocol that lacks a builtin retransmission's of packages and congestion control features, that are present in TCP. Because of this, the application layer must implement these features itself, and audit reliability and fairness oversharing bandwidth.

  The ongoing peer wire protocol consists of a handshake followed by a never-ending stream of length-prefixed messages. The handshake starts with character nineteen (decimal) followed by the string 'Bit Torrent protocol'. The leading character is a length prefix, put there in the hope that other new protocols may do the same and thus be trivial distinguishable from each other.

  All later integers sent in the protocol are encoded as four bytes big-endian.

  After the fixed headers come eight reserved bytes, which are all zero in all current implementations

  Next comes the 20 byte SHA1 hash of the bencoded form of the info value from the metainfo file. (This is the same value which is announced as info_hash to the tracker, only here it's raw instead of quoted here). If both sides don't send the same value, they sever the connection. The one possible exception is if a downloader wants to do multiple downloads over a single port, they may wait for incoming connections to give a download hash first, and respond with the same one if it's in their list.

  After the download hash comes the 20-byte peer id which is reported in tracker requests and contained in peer lists in tracker responses. If the receiving side's peer id doesn't match the one the initiating side expects, it severs the connection.

  That's it for handshaking, next comes an alternating stream of length prefixes and messages. Messages of length zero are keepalives, and ignored. Keepalives are generally sent once every two minutes, but note that timeouts can be done much more quickly when data is expected.

*** Rarest First

# (citeme: 000 this is the first paper i ever read, the one who start it all!)

BitTorrent motivates peers to keep contributing to the network and maintain overall reciprocity within the swarm through several key mechanisms, one of which being the *Rarest First* (RF) piece selection strategy.

The BitTorrent's protocol, when selecting pieces to the next request, peers often prioritize the *rarest piece* among their connected neighbours, typically the pieces held by the fewest peers in their local cluster within the swarm. Moreover, the "local rarest first" approach have several benefits. As ensuring that peers are able to acquire unique or uncommon pieces, allowing for them to later upload them back to the network, propagating further this rarest pieces, thus improving overall reciprocity chances.

By spreading rare pieces more efficiently, it reduces the likelihood that individual piece become unavailable, thus trying to mitigate whether a seeder departs from the swarm. Also, common pieces are deferred until later, trying to prevent redundant downloads from the seeder and allowing it to propagate more chunks and to more leechers efficiently.

In swarms with increase constrains, imbalance by low quantity of seeders and high amount of leechers, rarest first algorithm significantly outperforms naive sequential or random peer selection. In case of many leechers concurrently request the same piece from the seeder, redundant transfers take place wasting resources. Instead, the rarest first algorithm tries to motivate peers to fetch different pieces from other peers, thus distributing further the load between low consumed seeders.

This is paramount when the original seeder goes offline, condemning the torrent to an uncertain state, where a swarm may not be able to have all the pieces necessary to complete a file download, marking that torrent as irrecoverable. Therefore, *Rarest First* mitigates this by aggressively replicating the scarcest pieces first, thereby minimizing the chance of piece loss and enhancing swarm scalability and substantially.

In order to solve this issue, a client initially selects random pieces until at least has completed one full piece, in some implementations 4 pieces are chosen randomly. Once a peer has something to offer, it switch's back to the standard rarest piece implementation. Therefore, solving the issue when a peer has no pieces yet, which blocks him to upload to the network, therefore can't benefit from reciprocity. Hence, this algorithm promotes piece diversity over the swarm, reduces dependency on seeders, and distributes to further peers scarcest pieces, greatly improving swarm robustness and scalability.


*** End Game Mode

On BitTorrent downloading process, towards the very end a common problem arises, where the last few missing sub-pieces may be requested by slower peers. As a result, it can create a significant delay on the download process, which may block the transfer all together, not only harming his performance, but the overall network. Because it will take more time to become a seeder, creating a cyclical pattern that eventually will spread within the swarm.

In order to prevent this issue, some BitTorrent clients active the *End Game Mode*, when all remaining sub-pieces are already being requested. This mode, prevents bottleneck by aggressively send duplicate requests for every remaining sub-piece to all known peers that might have it. Hence, creating flooding of requests to ensure the client can obtain the final pieces from whoever delivers them first. However, this solution wastes an excessive amount of bandwidth and may clog other peers.

Taking this into account, as soon as a sub-piece arrives from any peer, a client immediately cancels all duplicate requests for the same sub-piece from other peers. Actually the protocol relies on the BitTorrent's "cancel" message, to honour this approach.

Almost all modern clients already implement this behaviour by default, where the sources [cite] suggest *mainline BitTorrent*, *libtorrent*, *Transmission*, *qBittorrent*. Moreover, they present empirical measurements that effectively show that it significantly reduces latency without much noticeable overhead.


*** Choking Algorithm (Tit-for-Tat Incentive Mechanism)


(Citation: The foundational choking algorithm was introduced by Bram Cohen in "Incentives Build Robustness in BitTorrent" [Cohen, 2003], which remains the seminal paper on BitTorrent's incentive design. Subsequent empirical validations, such as Legout et al. [2006, 2007], confirm that rarest-first combined with the choking algorithm is sufficient for efficient piece diversity, reciprocity, and robustness against free-riders.)
BitTorrent operates without any centralized resource allocation or global coordinator. Each peer independently seeks to maximize its own download rate in a decentralized manner. To achieve this while encouraging cooperation and discouraging free-riding (peers that only download without uploading), BitTorrent employs a variant of the tit-for-tat strategy from repeated game theory.
Peers cooperate by unchoking (allowing uploads to) selected neighbors and withhold cooperation by choking (temporarily refusing to upload to) others. Choking is a soft, temporary refusal: the choked peer can still receive data if unchoked elsewhere, download metadata, or send control messages (e.g., HAVE, INTERESTED), and the TCP connection remains open—no renegotiation is required when unchoking occurs later.
Although the choking logic is not part of the core BitTorrent wire protocol (BEP-0003), it is essential for achieving good performance in real swarms. A well-designed choking algorithm can fully utilize available upload capacity, provide consistent download rates to participating peers, and offer strong resistance to pure free-riders.
Technical Details of the Choking Algorithm
Each BitTorrent peer (in leecher state) maintains a fixed number of unchoked upload slots—4 by default (configurable in most clients). This cap ensures TCP congestion control can reliably saturate the peer's upload bandwidth without excessive contention or overhead.
The key decision is which peers to unchoke. Selections are based strictly on the current download rate received from each interested neighbor (i.e., peers that have expressed INTERESTED and are downloading from the local peer).
Measuring these rates accurately is non-trivial due to short-term fluctuations (e.g., peers joining/leaving, temporary congestion). Early implementations used long-term transfer totals, but performance suffered because bandwidth availability changes rapidly. The standard approach (used in mainline BitTorrent and most modern clients like libtorrent-based ones) employs a rolling 20-second average of the download rate to smooth noise while remaining responsive.
To prevent wasteful oscillation ("fibrillation"—rapid choking/unchoking that prevents TCP from ramping up), peers re-evaluate and apply choking decisions only every 10 seconds. This interval is long enough for new TCP connections to reach full speed after unchoking.
