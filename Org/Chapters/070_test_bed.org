* Evaluation
:PROPERTIES:
:CUSTOM_ID: evaluation
:END:

This chapter evaluates the proof-of-concept implementation across four scenarios, validating both the functional correctness of the protocol stack and the effectiveness of the integrated security mitigations. While, evaluating the performance drawback between standard QUIC and with an anonymity overlay. Additionally, testing the interoperability between both TEE backends and software-only devices communicating without limitations, achieving higher trust level metrics that can be leverage later for complex admission frameworks. That said, every scenario aims to target a specific claim made in the design chapter.

** Testbed Setup
:PROPERTIES:
:CUSTOM_ID: eval_testbed_setup
:END:

The following scenarios are performed on two host machines within the same local home network (simulating a small private swarm), using a combination of local daemon processes and virtualization tools to get access to TEE technologies and to virtualize the i2pd instance. This setup is sufficient to demonstrate the protocol correctness, peer discovery, authentication, and TEE integration on a real world scenario without requiring a physical distributed network.

Taking this into consideration, each remote peer runs as an independent {{{mark(bqti)}}} daemon instance, segregated using distinct IPC socket paths configured via the {{{mark(BQTI\_INSTANCE)}}} environment variable. The swarm trust anchor is established by generating a shared CA root at the test setup, distributed and loaded by each node. Currently, this process is executed manually, by copying the cryptographic material into the {{{mark(swarm)}}} directory within the internal {{{mark(bqti)}}} state, of each node. That said, the following nodes must be configured: {{{mark(bootstrap)}}}, {{{mark(seeder)}}}, {{{mark(leech-soft)}}}, {{{mark(leech-tee)}}}, and {{{mark(mal)}}} (malware peer), each directory representing a testing local remote peer.

Furthermore, adversarial behaviour is enabled by compiling the proof-of-concept with the feature flags: {{{mark(ml\_forge\_token)}}}, {{{mark(ml\_replay\_token)}}}, and {{{mark(ml\_piece\_sub)}}}. Each, activating a specific attack vector without modifying the honest client codebase, and vice versa keeping the proof-of-concept as realistic as possible.
