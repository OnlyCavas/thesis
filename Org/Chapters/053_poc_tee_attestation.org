** Remote Attestation: TEE Integration
:PROPERTIES:
:CUSTOM_ID: poc_tee_attestation
:END:

Until this point, the previous software-level mitigations, such as proof-of-work, signed tokens, and I2P layer integration, establish a computational barrier against Sybil attacks and provide anonymity against de-anonymisation attacks, respectively. However, they do not ensure that all remote participants are playing by the swarm's rules and, in fact, are using a trustworthy client implementation. In reality, a malicious peer can pretend to be contributing and using the provided authenticated methods while running their own modified version, practising free-riding, corrupting data, substituting pieces, and engaging in other attacks detailed in previous sections. Without a hardware-rooted mechanism, there is no practical way to detect an unverified client.

Integrating Trusted Execution Environments addresses this gap by providing hardware-rooted remote attestation, allowing peers to identify and attest to one another and collectively promote fair play within the swarm. Hence, having the tools to cryptographically verify that a remote peer is running an unmodified client implementation and within genuine trusted hardware, before even admitting it into the swarm.

The implementation chapter demonstrates how these technologies can coexist with the established design model, combining it with both QUIC and I2P, in contrast, keeping a modular design that allows the user to turn off each feature at any time, promoting broader adoption, and providing a hardware-agnostic solution that grows stronger with each additional security layer. Despite software-only remote peers not supporting TEE, the objective is that they also must be able to verify and accept remote peers that do support TEE and such remote attestation. Keeping that in mind, in {{{mark(bqti)}}} the attestation report is requested only at swarm admission alongside the standard proof-of-work, thereby ensuring both computational effort and client authenticity. As explained before, TEE participation is additive: peers without hardware compatibility fall back to the software implementation and remain valid participants. Moreover, the concrete attestation flow and decentralisation trade-off are detailed in [[#impl_tee_remote_attestation][Section 4.9.5]].
