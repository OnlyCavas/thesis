As depicted in [[#poc_bt_over_quic][Section 3.4]], a single QUIC connection is maintained for the entire BitTorrent session with each remote peer. All protocol traffic is multiplexed over this connection using independent QUIC streams of different types. That said, two main categories of streams are used:

+ *Control streams*

  Unidirectional streams dedicate to control traffic {{{mark(DHT)}}}, {{{mark(PEX)}}} and {{{mark(BEP)}}} messages. That said, each peer maintains their own outbound control stream, thus a stall or backlog on one peer's control message doesn't block the other peer's control stream.

+ *Bidirectional Streams*

  These are used for single major requests, thus associated with data transfer. A new bidirectional stream is opened of each individual piece request, and it's responsible for deliver the piece blocks that compose the final piece for higher fidelity and speed, while allowing fine-grained multiplexing and independent flow control per request. As a result, if a piece request stalls it doesn't block all the others.

# 2. Recv center diagram — goes after the dispatch channel paragraph. Show N stream handler boxes (concurrent) all
#    pointing into one channel buffer, then one arrow from the channel into the main loop. Simple, but it makes the
#   actor model click visually without needing to read the prose.

All incoming stream handlers across every active peer connection, run concurrently as independent tasks, where each feeds into a single central dispatch channel that is consumed sequentially by the main loop. Meanwhile, a slow or stalled stream will never block its sibling from delivering to the channel, buffering incoming packets with a capacity of {{{mark(1024)}}} queued messages before any producer would feel the backpressure. This approach keeps the actor model in one place, allowing the main loop to route each arriving packet to the correct handler based on its protocol {{{mark(ID byte)}}}, without requiring locks across concurrent readers. By default, the implementation caps concurrent connections at 50 swarm participants, keeping the buffer well within its capacity under normal load.

*** Packet Topology
:PROPERTIES:
:CUSTOM_ID: impl_quic_packet_topology
:END:

# [change: !!! Actually correct implementation, make that compatibility man]
Each packet, regardless of protocol, is assembled identically on the wire:

#+begin_example
[ 4 bytes: big-endian length ][ 1 byte: protocol ID ][ payload ]
#+end_example

The first one byte ID discriminates the protocol carried in the payload, following bep specification:

| protocol ID  | Constant | Protocol         |
|--------+----------+------------------|
| {{{mark(0x00)}}} | (zero length) | Keep-alive    |
| {{{mark(0x09)}}} | 9  | DHT (BEP 5)                |
| {{{mark(0x14)}}} | 20       | BEP 10 extension (PEX, metadata)      |
| {{{mark(0x13)}}}   | 19       | BEP handshake (standard)     |

A keep-alive is a special case, defined by a four byte zero frame carries no ID byte or payload, and serves only to maintain the connection alive. In case of a packet malformation that packet is ignored and later discarded. Then, the payload is serialized using Bencode which is the natural encoding for DHT, which BEP 5 establishes, and was extended uniformly to PEX and BEP message for consistency. The change was motivated to keep a simpler codec, which handles three protocols after the ID byte is read. Although, a trade-off is justified by the absence of any QUIC-native BitTorrent implementation to interoperate with to this date. Additionally, bidirectional streams, extend the default packet adding a reply handle to be able to respond back to the requesting stream without additional routing.

*** Connection Management
:PROPERTIES:
:CUSTOM_ID: impl_quic_management
:END:

The current implementation {{{mark(Connection Manager)}}} handles three edge cases that arise within the PoC network context: *self connections*, *simultaneous dials*, and *duplicate dials attempts*.

# 3. Simultaneous dial sequence diagram — goes in Connection Management after the tiebreaker paragraph. Two peers,
#  both dialing at the same time, the comparison happening on each side, one connection closing. A sequence
# diagram with 4-5 steps. This one shows the examiner you thought about a real race condition.

To prevent self-connection attempts before the handshake even begins, the implementation rejects them as early as possible. When the endpoint is bound to an unspecified address {{{mark((0.0.0.0))}}}, the manager determines its actual outbound IP by probing a local UDP socket. Later, it compares this resolved address and port against the target peer's address. A match on both is rejected immediately.

Fixing simultaneous dials where two different peers attempt to connect to each other at the same time, is solved by comparing the socket addresses lexicographically. As a result, both peers apply the same rule, if the local address is lower than the peer's, the incoming connection wins and the outgoing one is terminated, otherwise the outgoing connection replaces the incoming one. As both sides evaluate the same underlying comparison, they always converge on the same connection without coordination.

Finally, duplicate dial attempts are prevented by checking in-progress handshakes, before opening a new connection the manager checks both established connections and in-progress dials under a read lock. Thus, preventing races without holding a write lock across the network round-trip.

The endpoint is abstracted behind a NetworkEndpoint enum that abstracts connections and acceptance details regardless of whether the underlying transport is standard QUIC or I2P.
